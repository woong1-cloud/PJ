# 주간회의 개편 설계 — 요건을 확인하는 자리로

2026-09-01

회의를 "누가 맡나"가 아니라 "이게 뭔가"를 정하는 자리로 바꾼다.

---

## 왜 지금인가

### 회의의 정체가 화면과 다르다

지금 주간회의 화면은 배정 도구다. 행에서 할 수 있는 것이 **담당자와 예상일**
둘뿐이다. 그런데 실제 회의에서 가장 자주 나오는 결론은 이것이 아니라

> 정책을 다시 정해야 한다 / 요건이 명확하지 않다 / 이게 무슨 요청인지 확인이 필요하다

이다. 회의가 하는 일과 화면이 주는 도구가 하나도 안 겹친다.

### 요건이 실제로 얇다

미종결 21건의 To-Be 글자 수:

```
11, 15, 21, 21, 22, 24, 26, 28, 29, 32, 35, 47, 58, 67, 93, 94, 99, 141, 327, 609, 649
```

**중앙값 32자.** 절반이 한 줄이다. 검토중인 한 건은 To-Be 가 11자
(`N개 이상 구매 / 1+1, 2+1`)에 As-Is 가 아예 없다. 첨부 없음 16/21(76%),
코멘트 없음 11/21, 카테고리 미분류 8건.

한 줄짜리 요청이 대부분이니 회의가 "이게 뭔 얘기죠?"로 시작하는 것이 당연하다.

### 물어봐도 기다리는 중인 것이 안 보인다

지금 요건을 물으려면 상세 → 코멘트 → @멘션 → 등록이다(회의 중 4단계). 그리고
답을 기다리는 동안 **그 건은 여전히 `검토대기 27일`로 남는다.** 화면은
"IT 가 27일째 안 집었다"고 말하는데, 공은 요청자에게 넘어가 있다.

즉 검토대기 중앙값 17일 중 일부는 우리 쪽 지연이 아닐 수 있고, 앱에 그
구분이 없다.

### 회의는 아직 0회 열렸다

`meeting_sessions` 0건이다. 그래서 이 설계는 **회의가 없어도 값어치가 있는
것부터** 담는다. 1절(확인 대기)이 그것이다 — 27일 된 건에 코멘트가 0개인 것은
회의와 무관하게 물어봤어야 할 일이다.

## 결정 요약

| 무엇 | 결정 |
|---|---|
| 확인 대기 | 상태가 아니라 **플래그**. 답이 오면 자동 해제 |
| 질문 통로 | 코멘트 + **메일**. 회의 화면에서 한 번에 |
| 답 판정 | **요청자가 코멘트를 달면 답이 온 것으로 친다** |
| 요건 얇음 | To-Be 30자 미만이면 표시 |
| 본문 | 행에서 접었다 편다. 상세로 안 들어간다 |
| 처분 | 보류·반려·중복을 행에서. 기존 `CloseReasonDialog` 재사용 |
| 마치기 | **확인 창을 먼저.** 메일은 되돌릴 수 없다 |
| 회의록 | **만들지 않는다** (아래) |

## 1. 확인 대기

### 상태가 아니라 플래그다

```sql
alter table requirements
  add column if not exists awaiting_answer_since timestamptz,
  add column if not exists awaiting_answer_comment_id uuid
    references requirement_comments(id) on delete set null;
```

`검토대기`·`검토중`과 직교하는 축이다. "일이 어디까지 갔나"와 "공이 누구에게
있나"는 다른 질문이고, 하나로 합치면 둘 다 흐려진다.

상태로 만들지 않는 이유가 하나 더 있다. **보류를 만든 지 나흘째다.**
`REQUIREMENT_STATUSES` 를 또 늘리면 상태 목록이 열둘이 되고, 그때부터 아무도
상태 가이드를 안 읽는다.

`awaiting_answer_comment_id` 를 함께 두는 이유: 회의 화면이 "무엇을
물어봤는지"를 그려야 한다. 그리고 이 포인터가 있으면 나중에 회의록이
필요해졌을 때 질문을 정확히 복원할 수 있다(6절).

`on delete set null` — 코멘트를 지워도 확인 대기 자체는 유지된다. 물어본
사실이 사라지는 것과 질문 글이 사라지는 것은 다르다.

### 무엇이 바뀌나

| 어디 | 확인 대기 건은 |
|---|---|
| 회의 안건 | 빠진다 |
| `멈춘 것` 칩 | 빠진다 — 우리가 안 집은 것이 아니다 |
| 회의 화면 `확인 대기` 칩 | 여기 모인다 |
| 요구사항 목록 | 그대로 보인다. 뱃지만 붙는다 |

목록에서 안 감추는 것이 요점이다. 요청자가 자기 건을 볼 때 **"내 답을
기다리는 중"** 이 보여야 한다. 감추면 물어본 사실 자체가 안 보인다.

`stalledDays` 는 계속 잰다. 보류와 같은 방식이다 — 답을 60일 안 주는 것도
드러나야 한다. 다만 `isStalled` 는 거짓으로 둔다(칩에서 빠지는 이유).

### 답이 왔다는 판정

**요청자가 그 건에 코멘트를 달면 확인 대기를 푼다.**

물어본 시각 이후, 작성자가 그 건의 `requester` 인 코멘트가 하나라도 있으면
답이 온 것이다. 판정을 코멘트 등록 라우트에서 즉시 한다 — 크론으로 미루면
"답했는데 화면이 그대로"인 구간이 생긴다.

정확하지 않다. 요청자가 답이 아닌 말을 달 수도 있다. **틀리는 방향이
안전해서 이렇게 한다** — 안건으로 다시 올라올 뿐이고 회의에서 보면 된다.
반대(답이 왔는데 안 올라옴)는 회의가 그 건을 영영 못 본다.

풀릴 때 물어본 사람에게 인앱 알림을 보낸다. 메일은 안 보낸다 — `EMAIL_EVENTS`
는 "지금 당신이 뭘 해야 하는" 것만 싣는데, 이건 다음 회의에서 볼 일이다.

### 질문 보내기

회의 화면 행의 `질문하기` → 한 칸 → 보내면

1. 그 건에 코멘트를 단다(작성자는 누른 사람)
2. 요청자에게 **메일**
3. `awaiting_answer_since` 와 `awaiting_answer_comment_id` 를 채운다

`EMAIL_EVENTS` 에 `'요건확인'` 을 더한다. 그 목록은 메일이 슬쩍 늘어나는 것을
막는 장치이고 테스트가 값을 못 박고 있으므로, 늘리는 것은 의도적인 결정이다.

**근거:** 지금 메일이 나가는 사건 여섯 중 요청자에게 가는 것은 회의배정
하나뿐이다. 그런데 요청자가 실제로 무언가 해야 하는 순간이 정확히 이것이다 —
답을 안 주면 그 건은 멈춘다. 상한은 건당 1통이고, 답이 오기 전에는 다시 안
나간다(`한 번 더 알림` 은 사람이 눌러야 나간다).

멘션 메일과 겹치지 않는다. 질문 본문에 `@요청자` 를 넣지 않는다 — 넣으면 한
사건에 두 통이 간다.

## 2. 요건 얇음

```js
// lib/requirementDepth.js
export const THIN_TOBE = 30;
export function isThin(requirement)  // To-Be 가 30자 미만
```

30자인 이유: 운영 21건의 To-Be 중앙값이 32자다. 절반에 붙는다. 그게 과하게
보일 수 있지만 **실제로 절반이 한 줄이다** — 뱃지가 사실을 말하고 있다.

회의 화면에만 붙인다. 요구사항 목록에도 붙이면 요청자가 자기 건에서 그것을
보고 "잘못 썼다"로 읽는다. 그건 등록 폼이 할 일이지 목록이 할 일이 아니다.

정렬에 쓰지 않는다. 회의 안건의 기본 정렬은 지금처럼 오래 멈춘 순이다 —
얇은 것부터 보면 방금 들어온 한 줄짜리가 3주 묵은 건을 밀어낸다.

## 3. 화면

### 행에서 본문을 편다

제목을 누르면 As-Is · To-Be · 첨부가 펼쳐진다. 상세 API 를 다시 부르지
않는다 — `/api/meeting` 이 처음부터 함께 내린다. 회의 중에 왕복이 있으면
안 쓴다.

첨부는 서명 URL 이 필요하다. 미종결 21건 중 첨부가 있는 건이 5건이라 양이
적고, 회의에서 그림이 있는 건은 그림이 결정적이다.

### 진행률

`21건 중 8건 봄` + 막대. 봤음은 **화면 안에서만** 산다(서버에 저장하지
않는다). 회의 한 번의 진행 표시이지 요구사항의 속성이 아니다.

자동으로 찍히는 것: 본문을 펴면, 담당자를 고르면, 질문을 보내면, 처분하면.
사람이 따로 누를 일이 거의 없다.

### 안건 정의를 바꾼다

기본 필터가 `오래 멈춘 순` → **`이번 회의 안건`** 이다. 정렬이 아니라 집합을
고르는 칸이라야 한다.

| 칩 | 무엇 |
|---|---|
| 이번 회의 안건 | 미종결 − 확인 대기 |
| 확인 대기 | 답을 기다리는 것 |
| 담당 없는 것 | 그대로 |
| 이번 주 완료 | 그대로 |

`이번 주 신규` 는 뺀다. 요약 숫자로 남기고 칩에서는 지운다 — 신규만 따로 볼
이유가 회의에 없고, 칩이 다섯이면 고르는 일이 일이 된다.

### 처분을 행에서

`⋯` 에 보류 · 반려 · 중복 병합. 사유가 필요한 둘은 `CloseReasonDialog` 를
그대로 쓴다(2026-08-28 에 만든 것). 중복 병합은 `MergeDialog` 를 쓴다.

코드 주석이 이미 약속한 "상세로 들어가지 않는다 — 회의는 건당 30초짜리
자리"를 실제로 지키는 것이다.

## 4. 마치기 확인

지금은 누른 **뒤에** "N건이 배정됐고 M명에게 알렸습니다"가 뜬다. 메일 발송은
되돌릴 수 없는데 확인이 사후다.

```
회의를 마칩니다
마치면 메일이 나갑니다. 되돌릴 수 없습니다.

  질문 2건      이재현, 허예린님에게 메일
  배정 3건      요청자 2명에게 메일
  보류 1건

              [그만두기]  [마치고 메일 보내기]
```

정해진 것이 없으면 그렇게 말한다 — "그래도 마치면 다음 회의 구간이 여기서부터
시작합니다". 빈 회의를 마치는 것도 정상이고, 그때 버튼을 막으면 구간이 계속
누적된다.

숫자는 서버에서 미리 계산해 내려준다(`GET /api/meeting/end-preview`). 화면이
세면 실제로 나갈 메일과 어긋난다 — 다른 사람이 그 사이에 배정했을 수 있다.

`회의 마치기` 버튼을 화면 위로 올린다. 지금은 21건을 다 지나야 보이는데,
그것이 이 화면이 세션임을 알려주는 유일한 표시다.

## 5. 회의록은 만들지 않는다

담을 것이 전부 이미 다른 곳에 있다.

| 담을 것 | 이미 어디에 |
|---|---|
| 질문 | 그 건의 코멘트 |
| 처분 | 활동 피드 (사유까지) |
| 배정 | 활동 피드 |
| 회의 구간 | `meeting_sessions.ended_at` |

그리고 회의록만 답하는 질문이 없다. "지난주에 뭘 정했더라"는 활동 피드가,
"물어본 것에 답이 왔나"는 `확인 대기` 칩이, "이번 주에 뭘 끝냈나"는
`이번 주 완료` 가 답한다.

읽을 사람도 없다. 실사용자가 둘이고 둘 다 회의에 있다. 요청자는 마치기
메일을 받는다.

**나중에 만들어도 데이터를 안 잃는다.** `meeting_sessions` 가 구간을,
`change_logs` 와 코멘트가 시각을, `awaiting_answer_comment_id` 가 질문을
가리킨다. 필요해지면 조회 화면만 만들면 그때까지의 회의가 전부 복원된다.

## 테스트

렌더 테스트는 없다. 테스트 환경이 `node` 라 DOM 이 없다.

**`lib/awaitingAnswer.js` (새 파일)**
- 물어본 뒤 요청자 코멘트가 있으면 답이 온 것이다
- 물어보기 **전**의 요청자 코멘트는 답이 아니다
- 실무자 코멘트는 답이 아니다
- 물어본 적이 없으면 언제나 거짓
- 코멘트가 없어도 죽지 않는다

**`lib/requirementDepth.js` (새 파일)**
- 29자는 얇고 30자는 아니다
- To-Be 가 없으면 얇다
- 공백만 있으면 얇다 (trim 후 센다)

**`lib/stalled.test.js` (기존에 추가)**
- 확인 대기 건은 `stalledDays` 를 계속 잰다
- 확인 대기 건은 `isStalled` 가 거짓이다 — 우리가 안 집은 것이 아니다

**`lib/emailContent.test.js` (기존)** — `EMAIL_EVENTS` 가 못이라 자동으로
깨진다. `'요건확인'` 을 더하는 것은 의도적인 결정이다.

**`lib/quickFilters.test.js` (기존에 추가)**
- `멈춘 것` 칩이 확인 대기 건을 안 센다

## 순서

| | 무엇 | 크기 | 회의 없이도 값어치 |
|---|---|---|---|
| ① | 확인 대기 (질문·메일·해제) | 중간 | **있음** |
| ② | 행에서 본문 펴기 · 요건 얇음 | 작음 | 없음 |

| ④ | 진행률 · 마치기 확인 창 | 작음 | 없음 |

①이 먼저다. 회의가 아직 한 번도 안 열렸으므로, 회의에만 값어치가 있는
②③④를 먼저 만들면 안 쓰이는 화면에 기능을 쌓게 된다. ①은 27일 된 건에
코멘트가 0개인 지금 상황에 바로 듣는다.

## 범위 밖

**한 건씩 보기 모드** — Parabol 식으로 큰 카드 하나씩 넘기는 방식. 화면을
띄워놓고 여럿이 진행하는 회의라면 맞지만, 그 회의가 어떻게 굴러가는지 아직
모른다. 목록 + 진행률이면 혼자 훑을 때도 쓸 수 있다.

**등록 폼 개선** — 요건이 얇은 근본 원인은 입구일 수 있다. 요청자가 As-Is /
To-Be 에 뭘 써야 할지 몰라 한 줄만 쓴다. 그쪽이 근본이지만 효과가 나오는 데
몇 주가 걸리고 **이미 쌓인 21건은 그대로 남는다.** 따로 다룬다.

**답 판정을 똑똑하게** — "이게 답인가"를 문맥으로 가리는 것. 지금은 요청자가
말하면 답으로 친다. 오탐이 회의 안건 한 줄이라 값싸다.

**확인 대기에 기한** — "3일 안에 답 없으면 자동 재촉". `한 번 더 알림` 을
사람이 누르는 것으로 시작한다. 자동 재촉은 요청자에게 가는 첫 자동 메일이라,
사람이 눌러 보고 그것이 실제로 필요한지 본 다음에 정한다.
