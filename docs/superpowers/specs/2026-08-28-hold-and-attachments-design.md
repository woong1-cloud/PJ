# 보류 · 코멘트 시안 · 요청일 필터 설계

쓰는 분들이 준 의견 셋을 반영한다. 진행하지 못하는 건을 담을 그릇을 만들고,
논의 중 나온 시안을 코멘트에 붙이고, 언제 들어온 요청인지로 거른다.

작성일 2026-08-28

업데이트 소식은 별도 스펙에 있다 —
`docs/superpowers/specs/2026-08-28-feedback-loop-design.md` 5절. 여기 셋보다
먼저 나가야 한다. 셋 다 소식에 올릴 변화라 소식이 먼저 있어야 얹힌다.

---

## 왜 지금인가

### 1. 반려된 6건 중 셋은 실제로 보류였다

| 사유 | 실제로는 |
|---|---|
| 그룹온라인에 직접문의 부탁드립니다 | 반려 |
| **비즈니스, API 개편 예정으로 반려합니다** | **보류** |
| 이벤트 내역 미설계로 기존 내역은 반려로 처리합니다 | 반려에 가까움 |
| **위치정보 사업자 신고 선행 필요** | **보류** |
| **요건 및 우선순위 하향** | **보류** |
| 1. SSO 로그인 — 타사 사이트에 지원하지 않습니다 | 반려 |

셋 다 "지금은 안 하지만 조건이 갖춰지면 한다"인데, 담을 그릇이 없어 반려로
밀어 넣었다. **반려는 종결이라 그 셋은 영영 안 돌아온다.**

그리고 쓰는 쪽에서 말했다 — *"오래된 건들이 다 정책이나 개발 이슈 등 다양한
내용으로 보류 처리가 필요해서 진행이 안 되는 건"*이다. 지금 검토대기 24건 중
상당수가 보류 대상이라는 뜻이고, **보류는 많이 생긴다.**

### 2. 시안이 원래 요청의 증거와 섞인다

첨부는 요구사항 단위다(`requirement_images`). 코멘트에는 첨부가 없다.

기획자가 논의 중 시안을 올리면 요구사항 첨부로 들어가고, 나중에 보면 어느
것이 As-Is 캡처이고 어느 것이 개선안인지 알 수 없다.

### 3. 언제 들어온 요청인지로 거를 수 없다

필터는 셀렉트 일곱(상태·카테고리·프로젝트·유형·담당자·채널·우선순위)뿐이고
날짜 축이 없다. 요청일은 47건 모두 채워져 있어 거르는 축으로 성립한다.

## 1. 보류

### 종결과 같은 자리에 두되 하나만 다르다

`CLOSED_STATUSES` 에 넣는다. 그러면 다음이 전부 공짜로 따라온다.

| 무엇 | 왜 맞나 |
|---|---|
| 목록 기본 숨김 | 보류가 많이 생기므로 섞이면 "지금 손볼 것"이 흐려진다 |
| 회의 안건에서 제외 | 보류한 건을 다음 주에 다시 물으면 보류한 뜻이 없다 |
| 지연(예상일 초과) 제외 | 보류 건의 예상일은 의미가 없다 |
| 사유가 배너로 | `closureReason` 이 이미 종결 사유를 그린다 |
| 메뉴에 `재개` 만 | `menuTransitions` 가 종결에 빈 배열을 준다 |

**딱 하나가 예외다 — 정체를 계속 잰다.**

```js
// lib/stalled.js
if (CLOSED_STATUSES.includes(status) && status !== HOLD_STATUS) return null;
```

종결은 끝난 것이라 시간을 셀 이유가 없지만, **보류는 끝난 게 아니라 미뤄둔
것**이다. 시간이 가는 것을 세야 잊히지 않는다.

### 기준이 상태마다 다르다

지금 `stalledDays >= STALL_DAYS` 비교가 네 곳에 흩어져 있다 — `lib/listRow.js`,
`lib/quickFilters.js`, `app/api/meeting/route.js`, `lib/headline.js`.

보류만 기준이 다르므로 **판정을 함수 하나로 모은다.** 안 그러면 보류가 어디선
정체이고 어디선 아닌 화면이 된다.

```js
// lib/stalled.js
export const HOLD_STALL_DAYS = 60;

export function stallThreshold(status) {
  return status === HOLD_STATUS ? HOLD_STALL_DAYS : STALL_DAYS;
}

export function isStalled({ status, stalledDays } = {}) {
  if (stalledDays === null || stalledDays === undefined) return false;
  return stalledDays >= stallThreshold(status);
}
```

네 곳을 전부 `isStalled` 로 바꾼다.

**60일인 이유.** 14일이면 보류한 다음 주에 다시 안건에 오른다 — 보류가 아무
일도 안 한 셈이다. 60일이면 두 달에 한 번 다시 묻는다. 위 셋("API 개편 예정",
"사업자 신고", "우선순위 하향") 중 어느 것도 두 달 안에 답이 나오기 어렵다.

### 잊히지 않게 하는 장치는 칩이다

목록 빠른 필터에 `보류` 칩을 더한다. 칩은 이미 건수를 그리므로 `보류 12` 가 늘
눈에 있다.

그 칩으로 들어가면 **60일 넘은 것은 붉게 `62일째 멈춤`** 으로 뜬다. 두 달이
지나도록 아무 진전이 없는 보류가 스스로 드러난다.

칩은 3차 이상에게만 준다. 요청자에게 "남의 건이 왜 보류인가"는 할 일이 아니다.

**회의 화면은 손대지 않는다.** 보류를 회의에 다시 올리면 "재촉하지 않는다"는
목적과 정면으로 어긋난다. 칩의 붉은 줄이 그 역할을 한다.

### 사유는 필수, 유형은 없다

`close` 라우트를 쓴다. 사유를 받고 보드 밖 상태로 보내는 일이 반려·취소와
똑같다.

**그 라우트 이름이 "종결"을 뜻하는데 보류는 종결이 아니다.** 이름이 어긋나지만
라우트를 새로 만드는 것보다 낫다 — 사유 검증·권한·로그·알림이 전부 같고,
나누면 한쪽만 고쳐지는 날이 온다. 주석으로 남긴다.

권한은 **3차 이상**이다. 반려와 같다 — 보류는 IT 의 판단이다. 취소만 4차도 한다.

유형(정책 대기 / 개발 이슈 / 우선순위 밀림)을 고르게 하지 않는다. **분류는 쓰는
사람보다 읽는 쪽이 잘한다.** 몇 건 쌓이고 실제 패턴이 보이면 그때 뽑는 것이
정확하고, 지금 짐작으로 만든 넷은 대부분 '기타'로 간다.

### 상태 목록에서의 자리

`REQUIREMENT_STATUSES` 에 `'보류'` 를 더한다. 반려 앞에 둔다 — 보드 상태 다음,
종결 셋 앞이다.

`BOARD_STATUSES` 에는 넣지 않는다. 보드 컬럼이 여덟이 되면 가로가 넘치고,
보류는 흐름 안이 아니라 흐름에서 벗어난 상태다.

DB CHECK 제약을 함께 고친다(마이그레이션 0025).

## 2. 코멘트 시안

### 컬럼 하나

```sql
alter table requirement_images
  add column if not exists comment_id uuid references requirement_comments(id) on delete cascade;
```

| `comment_id` | 뜻 |
|---|---|
| 있음 | 그 코멘트에 붙은 시안 |
| 없음 | 지금처럼 요구사항 첨부 |

기존 첨부 11개는 `null` 이라 지금과 똑같이 보인다.

`on delete cascade` 를 거는 이유: 코멘트를 지우면 거기 붙은 시안도 함께 지워져야
한다. 남겨 두면 요구사항 첨부로 되살아나 "지웠는데 그림이 남아 있다"가 된다.

### 무엇이 바뀌나

- **요구사항 첨부 조회**는 `comment_id is null` 만 가져온다. 안 걸면 코멘트
  시안이 요구사항 첨부에 섞인다 — 이 기능을 만든 이유가 사라진다.
- **코멘트 조회**가 자기 이미지를 함께 가져온다.
- **업로드**는 `commentId` 를 받으면 그 값을 함께 넣는다. 경로·스토리지·검증은
  그대로다.

### 화면

코멘트 입력창 아래에 작은 `＋ 이미지` 가 붙는다. 고른 파일은 등록 전까지
미리보기로 보이고, 코멘트를 등록하면 함께 올라간다.

**코멘트를 먼저 만들고 그 id 로 이미지를 올린다.** 순서를 뒤집으면 이미지가
붙을 코멘트가 없다. 이미지 업로드가 실패하면 코멘트는 이미 등록된 상태로
남는다 — 그때는 그 코멘트에 다시 붙일 수 있게 안내한다.

등록된 코멘트의 이미지는 인라인으로 보인다. 누르면 `Lightbox` 가 열린다 —
상세 재설계에서 만든 것을 그대로 쓴다.

### 권한

코멘트를 쓸 수 있으면 이미지도 붙일 수 있다(4차 포함). 지우는 것은 자기
코멘트만 — 코멘트 삭제 규칙을 그대로 따른다.

## 3. 요청일 필터

### 셀렉트 하나

`buildFilterFields` 에 여덟 번째를 더한다.

```
요청일 전체 ▾   →   이번 주 / 이번 달 / 지난 달 / 최근 3개월
```

값은 `thisWeek` · `thisMonth` · `lastMonth` · `last3Months` 다.

날짜 두 칸(시작~끝)으로 하지 않는 이유: 47건 규모에서 "9월 1일~15일"을 정확히
지정할 일이 드물고, 칸이 둘 늘면 필터바가 무거워진다. 필요해지면 그때 더한다.

### 서버에서 건다

`request_date` 가 date 타입이라 `gte`/`lte` 한 줄이다. 다른 필터가 전부 서버에서
걸리므로 이것만 화면에서 거르면 동작이 갈린다.

기준은 KST 다(`lib/overdue.js` 의 `todayInKst`). 서버가 UTC 라 그대로 쓰면
한국 시각으로 자정 직후에 "이번 주"가 어제로 잡힌다.

### 순수 함수

```js
// lib/dateRange.js
requestDateRange(key, today) -> { from, to } | null
```

`today` 는 `'YYYY-MM-DD'`. 모르는 키는 `null` — 주소를 손으로 고쳐 아무 값이나
넣는 길을 열어 두지 않는다.

### 배포예정일 필터는 만들지 않는다

47건 중 8건(17%)만 채워져 있다. 걸면 39건이 사라지고, 그것은 화면에서
**"없다"로 읽힌다.**

그 칸을 채우게 만드는 일이 선행이다 — 착수 창이 이미 예상일을 받고 있으므로,
그것이 실제로 채워지는지를 몇 주 보고 나서 판단한다.

## 범위 밖

**보류 사유의 유형** — 1절 참고. 패턴이 보이면 그때 뽑는다.

**보류를 회의 화면에** — 재촉이 된다. 칩의 붉은 줄이 대신한다.

**배포예정일 필터** — 3절 참고. 그 칸이 채워지는지 먼저 본다.

**코멘트 이미지 순서 바꾸기** — 요구사항 첨부에는 `sort_order` 가 있지만
코멘트 시안은 보통 한두 장이라 필요 없다.

**보류 일괄 처리** — 검토대기 24건 중 여럿을 한 번에 보류로 보내고 싶을 수
있다. 다만 사유가 건마다 다르므로 일괄로 하면 사유가 같아지고, 그러면 사유를
필수로 받은 뜻이 없어진다.
