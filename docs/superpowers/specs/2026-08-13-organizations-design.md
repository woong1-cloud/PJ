# 조직(소속) 체계 설계

전사 확산에 맞춰 가입 시 고르는 **소속**을 실제 조직명으로 바꾸고, 브랜드에
배치되지 않는 조직(법무팀·재무팀)도 프로젝트 진행을 볼 수 있게 한다.

작성일 2026-08-13

---

## 왜 지금인가

패션본부·법무팀·재무팀 등 브랜드 밖 부서가 MOA 를 쓰기 시작한다. 지금 구조는
그 사람들을 담지 못한다.

**1. 소속이 두 값뿐이다.** `AFFILIATIONS = ['브랜드', '본부']`. 패션본부도
법무팀도 재무팀도 전부 `본부` 하나로 뭉뚱그려져, 관리자가 배치 화면에서
누가 누군지 알 수 없다.

**2. 그 두 값이 등급을 제안한다.** `suggestTier` 가 `본부 → 3차(실무자)` 로
떨어뜨린다. 실무자는 상태 변경·담당자 지정·내용 수정을 할 수 있다. 법무팀
직원이 가입하면 그 등급이 미리 채워지고, 관리자가 제안값을 그대로 승인하는
순간 남의 요구사항 상태를 바꿀 수 있게 된다.

**3. 브랜드에 배치되지 않으면 아무것도 안 보인다.** `lib/projectAccess.js` 의
규칙은 "내가 배치된 브랜드에 전개된 프로젝트만". 재무팀이 전사 프로젝트
진행을 보려면 5개 브랜드 전부에 배치되거나(요구사항까지 전부 열림) 전체
관리자가 되어야 한다(브랜드 생성·삭제까지 열림). 둘 다 과하다.

**4. 목록을 늘리려면 배포해야 한다.** `JOB_ROLES` 는 코드 상수이자 DB CHECK
제약이다(`migrations/0012`). 값 하나 추가에 코드 수정 + 마이그레이션 + 배포가
필요하다. 조직은 직무보다 훨씬 자주 바뀐다.

## 결정 요약

| 결정 | 내용 |
|---|---|
| 소속을 실제 조직명으로 | `브랜드/본부` → `스파오`·`패션본부`·`법무팀` … |
| 조직 목록은 관리 화면에서 편집 | 전체관리자가 `/admin/organizations` 에서. 배포 불필요 |
| 조직 목록에 브랜드도 포함 | 가입 화면의 `근무 브랜드` 칸 삭제 |
| 등급 제안은 조직이 갖는다 | 조직별 `default_tier`, 비면 요청자(4차) |
| 전사 열람은 별도 축 | 등급이 아니라 `can_view_all_projects` 플래그 |
| 직무(`JOB_ROLES`)는 이번에 건드리지 않는다 | 소속이 대부분을 말하게 되므로 |

## 1. 데이터 모델

### 새 테이블 `organizations`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid pk | |
| `name` | text not null unique | `스파오`, `패션본부`, `법무팀` |
| `brand_id` | uuid null → `brands(id)` | 이 조직이 브랜드면 연결. 법무팀은 null |
| `default_tier` | text null | 가입 승인 화면 제안값. `'1차'`~`'4차'` |
| `default_view_all_projects` | boolean not null default false | 전사 열람 제안값 |
| `is_active` | boolean not null default true | |
| `sort_order` | int not null default 0 | 가입 화면 목록 순서 |

**그룹은 컬럼이 아니라 `brand_id` 로 판정한다.** 있으면 `브랜드`, 없으면
`본부·팀`. 그룹 컬럼을 따로 두면 언젠가 `brand_id` 와 어긋나고, 그때 어느
쪽이 진실인지 알 수 없다.

**삭제하지 않고 끈다.** 그 조직으로 가입한 사람의 소속 기록이 깨지면 안 된다.
꺼진 조직은 가입 화면 목록에서 빠지지만 기존 팀원 표시에는 남는다.

### `team_members` 변경

| 컬럼 | 변경 |
|---|---|
| `organization_id` | **추가** — uuid null → `organizations(id)` |
| `can_view_all_projects` | **추가** — boolean not null default false |
| `affiliation` | **남긴다** — 삭제하지 않음 |

`affiliation` 을 지우지 않는 이유: 지금 가입해 있는 사람의 `'브랜드'`/`'본부'`
값이 사라지면 관리자가 그 사람이 누구였는지 알 방법이 없다. 화면은
`조직 이름 ?? 옛 소속값 ?? '—'` 순으로 떨어진다.

## 2. 권한 — 두 축을 나눈다

지금 등급(요청자 → 실무자 → 실무 관리자 → 전체 관리자)은 **브랜드 안에서의
사다리**다. 재무팀이 필요한 것은 사다리를 오르는 게 아니라 **브랜드를
가로지르는 읽기**다. 세로 축으로 가로 요구를 표현하려니 어느 칸에 넣어도
틀린다. 그래서 축을 하나 더 둔다.

```
세로축  user_brand_roles.tier          브랜드마다 무엇을 할 수 있는가
가로축  team_members.can_view_all_projects   브랜드를 넘어 무엇을 볼 수 있는가
```

### 전사 열람이 켜진 사람이 보는 것

| | |
|---|---|
| 볼 수 있다 | 전사 프로젝트 목록 · 브랜드별 전개 상태 · 진척률 |
| 볼 수 없다 | 배치되지 않은 브랜드의 요구사항 건별 목록(제목·내용) |
| 할 수 있다 | 없음. 읽기 전용 |

코드가 이미 두 축으로 갈라져 있어 앞쪽만 넓히면 된다.

- `visibleProjects` / `canSeeProject` — 프로젝트가 보이는가 → **넓힌다**
- `requirementsOfMyBrands` — 건별이 보이는가 → **그대로**
- `visibleRequirements` — 비공개 건인가 → **그대로**

```js
canSeeProject({ projectBrands, myBrandIds, isGlobalAdmin, canViewAllProjects })
```

`canViewAllProjects` 가 참이면 전개 브랜드와 무관하게 `true`. 순수 함수라
테스트로 경계를 고정한다.

### 자기 부여를 막는다

조직의 `default_tier` 와 `default_view_all_projects` 는 **제안값일 뿐이고
확정은 관리자가 한다.** 소속은 가입자가 스스로 고르는 자기 신고이므로,
'재무팀' 을 골랐다는 이유로 전사 열람이 자동으로 켜지면 그건 스스로 권한을
부여하는 길이 된다.

같은 이유로 공개 가입 API 는 `default_tier` 와
`default_view_all_projects` 를 **내려보내지 않는다.** 가입 화면에 필요한
것은 이름과 그룹뿐이다.

### 로그인 후 착지

전사 열람이 켜졌지만 브랜드에 하나도 배치되지 않은 사람은 요구사항 목록이
비어 있다. 로그인 직후 그 화면으로 보내면 고장난 줄 안다. **브랜드가 0개이고
전사 열람이 켜진 사람은 `/projects` 로 보낸다.**

`app/login/page.js:100` 의 `router.push('/requirements')` 가 분기 지점이다.

## 3. 가입 화면

```
이름            [김온라인            ]
이메일          [kim@eland.co.kr    ]
비밀번호 · 확인  [••••••] [••••••]
소속            [스파오          ▾]   ← 조직 목록, 그룹으로 나뉨
직무            [온라인 MD       ▾]
                 (근무 브랜드 칸 삭제)
```

소속 셀렉트는 두 그룹으로 나눈다. 조직이 20개쯤 되면 한 줄로 늘어놓을 수 없다.

```
브랜드     스파오 · 미쏘 · 로엠 · 후아유 · 뉴발란스
본부·팀    패션본부 · 온라인BU · 법무팀 · 재무팀
```

`근무 브랜드` 칸을 없애는 근거: 조직이 이미 `brand_id` 를 알고 있다. 같은
정보를 두 번 묻는 칸이다.

### 조직 조회에 실패하면

소속은 필수이므로 가입 자체가 불가능하다. **명시적 오류를 띄우고 제출을
막는다.** 빈 셀렉트를 보여주면 사용자는 자기가 뭘 잘못했는지 찾다가 포기한다.
기존 브랜드 목록 조회 실패와 같은 처리다.

## 4. 관리자 승인 화면

`/admin/members` 의 배치 다이얼로그가 조직에서 두 값을 미리 채운다.

| | 스파오 온라인팀원 | 법무팀 직원 |
|---|---|---|
| 소속 | `스파오` | `법무팀` |
| 조직의 `brand_id` | 스파오 | 없음 |
| 배치할 브랜드 | 자동 `스파오` | **관리자가 직접 선택** |
| 등급 | 자동 `요청자` | 자동 `요청자` |
| 전사 열람 | 꺼짐 | 조직에 켜 두었다면 켜짐 |

전사 열람의 기본값은 조직마다 관리자가 정한다. 법무팀·재무팀에 켜 둘지는
운영 판단이고, 코드가 조직 이름을 보고 정하지 않는다 — 이름으로 권한을
추론하기 시작하면 `법무팀2` 같은 조직이 생겼을 때 조용히 어긋난다.

법무팀 사람은 "어느 브랜드 일로 들어왔는지" 를 데이터가 모른다. 추측해서
채우면 틀린 값이 맞는 값처럼 보이므로 비워 두고 관리자가 정한다.

### 등급 한 줄 설명

`실무자` 와 `실무 관리자` 는 이름만으로 한눈에 안 갈린다. 라벨 자체는
도움말·온보딩에 이미 퍼져 있어 그대로 두고, `lib/tiers.js` 에 `TIER_HINTS`
를 더해 셀렉트 아래에 한 줄을 붙인다.

| 라벨 | 한 줄 |
|---|---|
| 요청자 | 요구사항을 올리고 검토를 요청합니다 |
| 실무자 | 상태와 담당자를 바꿉니다 |
| 실무 관리자 | 팀원을 배치하고 카테고리를 관리합니다 |
| 전체 관리자 | 브랜드와 조직을 만듭니다 |

## 5. 조직 관리 화면

**`/admin/organizations`** — 전체관리자 전용 새 페이지.

`/admin/brands` 에 섹션으로 붙이지 않는 이유: 그 화면은 이미 브랜드 목록·팀
배치·전체관리자 토글로 붐빈다. 조직은 가입 화면에 직접 노출되는 목록이라
따로 다룰 값어치가 있다. 구조는 `components/CategorySettings.jsx`(173줄)와
같으므로 그것을 본뜬다.

| 화면 | 내용 |
|---|---|
| 목록 | 이름 · 연결 브랜드 · 기본 등급 · 전사 열람 · 사용 여부 |
| 추가/수정 | 이름, 브랜드 연결(선택), 기본 등급(선택), 전사 열람(체크), 순서 |
| 끄기 | 비활성 토글. 삭제 버튼은 두지 않는다 |

### API

| 라우트 | 권한 | 비고 |
|---|---|---|
| `GET/POST /api/organizations` | 전체관리자 | |
| `PATCH /api/organizations/[id]` | 전체관리자 | 이름·연결·기본값·`is_active` 수정 |
| `GET /api/signup/organizations` | **비로그인 공개** | `id`·`name`·그룹만. 등급·플래그는 내려보내지 않는다 |

`DELETE` 라우트는 **만들지 않는다.** 끄는 것은 `PATCH` 로 `is_active` 를
false 로 바꾸는 것이고, 진짜 삭제는 그 조직으로 가입한 사람의 소속 기록을
깨뜨린다. 지울 길을 열어 두면 언젠가 눌린다.

## 6. 마이그레이션 `0022`

1. `organizations` 생성
2. `team_members.organization_id`, `team_members.can_view_all_projects` 추가
3. 브랜드 5개를 조직으로 시드 — 스파오·미쏘·로엠·후아유·뉴발란스,
   `brand_id` 연결, `default_tier = '4차'`
4. `affiliation='브랜드'` 이고 `requested_brand_id` 가 있는 멤버 →
   해당 조직으로 연결
5. `affiliation='본부'` 인 멤버 → **비워 둔다.** 어느 본부인지 데이터에 없다
6. `affiliation` 컬럼은 남긴다

본부 소속 기존 멤버는 관리자가 `/admin/members` 에서 조직을 지정한다.
마이그레이션이 추측해서 채우면 틀린 값이 맞는 값처럼 보인다.

## 7. 순수 함수와 테스트

| 함수 | 파일 | 고정할 규칙 |
|---|---|---|
| `groupOrganizations(orgs)` | `lib/organizations.js` | `brand_id` 유무로 두 그룹. 비활성 제외. `sort_order` 순 |
| `suggestTierFromOrg(org)` | `lib/organizations.js` | 조직이 없거나 `default_tier` 가 비거나 모르는 값이면 `'4차'` |
| `displayAffiliation(member)` | `lib/organizations.js` | `조직 이름 ?? affiliation ?? '—'` |
| `canSeeProject(...)` | `lib/projectAccess.js` | `canViewAllProjects` 참이면 전개 브랜드와 무관하게 참 |

`suggestTier(affiliation)` 는 **지운다.** 두 함수가 공존하면 어느 쪽이 실제로
쓰이는지 불분명해진다.

판단이 안 될 때 권한을 더 주는 쪽으로 기울지 않는다는 기존 규칙을 그대로
따른다 — 모르는 값은 전부 가장 낮은 등급으로 떨어진다.

## 범위 밖

- **직무(`JOB_ROLES`) 확장** — 소속이 실제 조직명이 되면 "이 사람이 누구인가"
  의 대부분을 소속이 말한다. 직무는 조직 안에서의 역할로 좁혀지고 지금 8개로
  대체로 덮인다. `법무`·`재무` 를 직무에도 넣으면 소속과 같은 말을 두 번 한다.
- **조직 계층(본부 → 팀)** — 지금 필요한 것은 평평한 목록이다. 계층이 실제로
  필요해지는 시점에 `parent_id` 를 더한다.
- **전사 열람자의 요구사항 건별 조회** — 프로젝트 단위까지가 요구다.
  건별까지 열려면 비공개 판정과 브랜드 판정을 다시 설계해야 한다.
