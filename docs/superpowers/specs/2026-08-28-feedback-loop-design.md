# 소통 루프 설계 — 의견 · 소식 · 회의 성과

쓰는 사람이 의견을 남기고, 그것이 반영되면 소식으로 돌아오게 한다. 그리고
주간회의가 밀린 것만 보는 자리가 되지 않게 한다.

작성일 2026-08-28

---

## 왜 지금인가

**1. 3주 동안 네 번의 큰 변화가 나갔는데 안내가 한 번도 없었다.**

| 무엇 | 언제 |
|---|---|
| 주간회의 화면 + 안건 메일 | 8/26 |
| 상세 화면 재설계 | 8/26 |
| 반려 사유 표시 | 8/28 |
| 목록 세 뷰 + 상세 중복 병합 | 8/28 |

마지막 것은 **기본 화면이 표에서 목록으로 바뀐다.** 쓰던 사람은 로그인했다가
화면이 달라진 것을 보고 고장인지 바뀐 것인지 알 수 없다.

**2. MOA 는 요구사항 관리 도구인데 자기 요구사항을 받을 곳이 없다.**

지금은 쓰는 사람이 전체 관리자에게 직접 말해야 한다. 그 말은 기록되지 않고,
반영됐는지도 알 수 없다.

**3. 주간회의 화면이 밀린 것만 보여준다.**

`/api/meeting` 이 미종결 건만 가져온다(`route.js:38`). 회의 메일에는
`이번 주 움직인 것` 블록이 있는데 화면에는 없다 — **메일과 화면이 어긋나
있었다.** 요약 칩 셋도 전부 문제를 세는 숫자다(멈춤 · 담당 없음 · 신규).

세 가지가 한 고리다. **의견이 올라오고 → 읽고 → 고쳐서 배포하고 → 소식으로
알린다.** 지금은 그 고리의 어느 마디도 없다.

## 결정 요약

| 결정 | 내용 |
|---|---|
| 의견 폼 | **한 칸.** 종류·우선순위·화면 경로를 묻지 않는다 |
| 분류 | 쓰는 사람이 아니라 읽는 쪽이 한다 |
| 의견 알림 | 전체 관리자에게 **메일** |
| 관리 화면 | `/admin/feedback` 목록 + 상태 셋 |

| 소식 노출 | 로그인 후 안 본 것이 있으면 한 번 |
| 회의 화면 | 이번 주 완료 칩과 보기를 더한다 |
| 순서 | ③ 회의 → ② 소식 → ① 의견 (셋이 독립이라 따로 배포할 수 있다) |

## 1. 의견 보내기

### 어디에

계정 메뉴의 `도움말` 아래에 `의견 보내기` 를 둔다. 새 화면을 만들지 않고 창
하나다.

떠 있는 버튼으로 두지 않는 이유: 목록 화면이 이미 플로팅 등록 버튼을 쓰고
있어 모바일에서 겹친다.

### 무엇을 받는가

**한 칸이다.**

```
모아를 쓰면서 불편한 점이나 바라는 것을 적어 주세요.
짧아도 괜찮습니다. 읽고 반영되면 알려드립니다.

[                                    ]

                              [보내기]
```

종류(오류/개선/문의)를 묻지 않는다. **분류는 쓰는 사람보다 읽는 쪽이 잘한다.**
그리고 칸이 늘수록 "이 버튼 좀 작아요" 같은 가벼운 말이 안 올라온다.

화면 경로도 담지 않는다. 자동이라 부담은 없지만, 받는 값이 늘면 나중에 그것을
근거로 판단하게 되고 그 판단이 틀릴 수 있다 — 지금은 사람이 쓴 문장 하나가
가장 정확하다.

### 요구사항 흐름으로 받지 않는 이유

'모아' 브랜드를 만들어 요구사항으로 받는 안이 있었다. 목록·상태·코멘트·알림이
전부 공짜로 따라오고 도그푸딩도 된다.

**요구사항 등록 폼이 무겁다는 것이 결정적이다.** As-Is · To-Be · 카테고리 ·
채널 · 우선순위를 다 채워야 한다. 가벼운 의견을 남기려고 그것을 통과해야 하면
아무도 안 쓴다. 게다가 19명을 그 브랜드에 배치해야 하고 브랜드 셀렉터에
'모아'가 끼어든다.

대신 관리 화면에서 **요구사항으로 승격**할 수 있게 한다(4절). 가벼운 것은
가볍게 받고, 무거운 것만 무거운 흐름으로 넘긴다.

### 데이터

```sql
create table moa_feedback (
  id uuid primary key default gen_random_uuid(),
  member_id uuid not null references team_members(id),
  body text not null,
  status text not null default '새로 옴'
    check (status in ('새로 옴','확인함','반영함')),
  -- '반영함' 으로 바꿀 때 받는 한 줄. 그대로 낸 사람에게 간다.
  admin_note text,
  -- 요구사항으로 승격한 경우 그 건. 승격은 관리 화면에서만 한다.
  requirement_id uuid references requirements(id),
  created_at timestamptz not null default now(),
  resolved_at timestamptz
);
```

`brand_id` 를 두지 않는다. 의견은 모아 전체에 대한 것이지 어느 브랜드의
것이 아니다.

## 2. 의견 알림 — 메일

의견이 올라오면 **전체 관리자 전원에게 메일**이 간다.

인앱 알림을 쓰지 않는 이유: 지금 110건 중 105건이 안 읽혔다. 이미 아무도 안
보는 통로에 하나를 더 얹으면 그 하나도 안 읽힌다.

`EMAIL_EVENTS` 에 `'의견'` 을 더한다. 그 목록은 메일이 슬쩍 늘어나는 것을 막는
장치이고 테스트가 값을 못 박고 있으므로, 늘리는 것은 의도적인 결정이다.

**상한이 있다.** 지금 활성 19명 중 실사용 4명이라 주 1~2건을 넘기 어렵다.
그보다 많아지면 묶어 보내는 쪽으로 다시 봐야 한다.

메일 문구:

> **[모아 MOA] 새 의견 — 박천주**
>
> 목록에서 제목이 잘려서 뭔지 알아보기 어렵습니다.
>
> https://moa.noavibe.app/admin/feedback

## 3. 관리 화면

`/admin/feedback` 한 장. 전체 관리자 전용이다.

목록은 새로 온 것이 위다. 각 줄에 사람 · 날짜 · 내용 · 상태가 있다.

| 상태 | 뜻 |
|---|---|
| **새로 옴** | 아직 안 읽음 |
| **확인함** | 읽었고 지금은 안 함 |
| **반영함** | 고쳤음 |

**분류·우선순위 칸을 만들지 않는다.** 칸을 만들면 관리자가 매번 채워야 하고,
그 분류는 나중에 읽을 때 하면 된다.

`반영함` 으로 바꿀 때 **한 줄 메모**를 받는다. 그 문장이 그대로 낸 사람에게
간다.

> 의견 주신 것 반영했습니다 — 목록에서 제목이 안 잘리게 했습니다.

메모 없이는 `반영함` 으로 못 바꾼다. 반려 사유를 필수로 받는 것과 같은
이유다 — 무엇이 어떻게 반영됐는지 없으면 낸 사람은 그냥 닫혔다고 읽는다.

## 4. 요구사항으로 승격

관리 화면의 줄마다 `요구사항으로` 버튼이 있다.

누르면 요구사항 등록 창이 열리고 **제목과 To-Be 에 의견 내용이 미리 채워진다.**
등록하면 `moa_feedback.requirement_id` 에 그 건이 이어지고 상태가 `확인함`
으로 바뀐다.

브랜드는 관리자가 고른다. 의견에는 브랜드가 없으므로 자동으로 정할 수 없다.

## 5. 업데이트 소식

### 코드에 둔다

`lib/newsItems.js` 에 배열로 둔다. `lib/onboarding.js` 와 같은 방식이다.

```js
export const NEWS = [
  {
    date: '2026-08-28',
    title: '요구사항 목록을 세 가지로 볼 수 있습니다',
    body: '목록·표·보드 중에서 고르세요. 기본이 목록으로 바뀌었고, 표를 쓰시던 분은 한 번 고르면 계속 표로 열립니다.',
  },
];
```

관리 화면을 만들지 않는 이유: 소식은 배포와 함께 나가는 것이라 **배포 없이 올릴
일이 없다.** 화면을 만들면 관리자가 쓸 자리가 하나 더 늘어난다. 조직·직무를
관리 화면으로 뺀 것과 판단이 다른 이유는, 그쪽은 배포 없이 자주 바뀌는 값이기
때문이다.

### 큰 변화만

작은 고침은 담지 않는다. 담기 시작하면 목록이 길어지고, 길어진 목록은 아무도
안 읽는다.

기준은 **"쓰던 사람이 로그인했을 때 화면이 달라 보이는가"** 다.

### 언제 보여주는가

로그인 후 **안 본 소식이 있으면 한 번** 뜬다. `team_members.news_seen_at` 에
마지막으로 본 시각을 적는다 — `onboarded_at` 과 같은 방식이다.

첫 로그인 안내(`WelcomeDialog`)와 겹치면 **안내가 먼저다.** 처음 온 사람에게
"뭐가 바뀌었습니다"는 의미가 없다. 안내를 닫고 나면 그때 `news_seen_at` 을
지금으로 찍어 소식 창이 안 뜨게 한다.

다시 보려면 계정 메뉴의 `업데이트 소식` 으로 들어간다.

### 순수 함수

```js
unseenNews(news, seenAt) -> NewsItem[]
```

`seenAt` 이 없으면(한 번도 안 봄) 전부, 있으면 **그보다 나중 날짜만**. 날짜
내림차순이다.

**날짜만 비교한다.** `seenAt` 은 시각까지 담기지만(`onboarded_at` 과 같은
`timestamptz`), 앞 열 글자만 잘라 항목의 날짜와 견준다. 같은 날짜는 본 것으로
친다 — 안 그러면 8/28 에 소식을 보고 나서도 그날 내내 창이 다시 뜬다.

**따라서 같은 날짜의 항목 둘은 한 묶음이다.** 하루에 두 번 배포하면서 소식을
따로 적으면 두 번째를 놓친다. 그럴 때는 한 항목으로 합치거나 날짜를 다음 날로
민다 — 소식은 큰 변화만 담으므로 하루에 둘이 나올 일이 드물다.

## 6. 주간회의 화면에 이번 주 완료를 더한다

### 지금 무엇이 빠져 있나

`/api/meeting` 이 미종결 건만 가져온다. 회의 메일에는 `이번 주 움직인 것`
블록이 있는데 화면에는 없다.

요약 칩 셋도 전부 문제를 세는 숫자다 — 멈춤 · 담당 없음 · 신규. **회의가
나쁜 소식 셋으로만 시작한다.**

### 무엇을 더하나

조회 범위를 넓힌다. 미종결 + **지난 7일 안에 완료된 건**이다. 종결 전체를
가져오면 완료 11건이 다 딸려와 목록이 흐려진다.

요약 칩과 보기 칩을 하나씩 더한다.

```
[14일+ 멈춤 9]  [담당 없음 24]  [이번 주 신규 3]  [이번 주 완료 2]

보기  (오래 멈춘 순) (담당 없는 것만) (이번 주 신규) (이번 주 완료)
```

마지막 칩은 초록이다. 나머지 셋이 붉고 노랗고 회색이라, 하나가 초록이면 그것이
성과라는 것이 색만으로 읽힌다.

완료 건 줄에는 정체 표시 대신 `8일 걸림` 과 승인 확인 내용이 붙는다.
`lib/listRow.js` 와 `lib/closureReason.js` 를 그대로 쓴다 — 목록·상세와 같은
문구가 나온다.

담당자·예상일 셀렉트는 완료 건에서 감춘다. 끝난 건의 담당자를 바꿀 일은 없다.

## 범위 밖

**의견에 대한 대화** — 코멘트를 달 수 있게 하면 요구사항의 축소판이 된다.
반영 메모 한 줄이면 지금 규모에 충분하다.

**소식에 "○○님 의견 반영" 표시** — 값어치는 있지만 소식 항목과 의견을 이어야
한다. 의견이 실제로 몇 건 쌓이는지 보고 정한다.

**의견 묶어 보내기** — 주 1~2건을 넘으면 그때 본다.

**회의 화면의 완료 건 드래그** — 완료는 승인 절차로만 도달하므로 보드와 달리
끌어 옮길 수 없다. 회의 화면에는 원래 드래그가 없다.
