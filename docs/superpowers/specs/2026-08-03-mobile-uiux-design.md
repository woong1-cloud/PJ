# 모바일 UI/UX 전면 재검토 설계

작성일: 2026-08-03

## 배경

배포 후 모바일에서 접속하니 상단 메뉴가 잘려 보인다는 보고가 들어왔다.
원인을 찾다가 더 근본적인 사실을 확인했다.

컴포넌트 30여 개와 화면 14개를 통틀어 반응형 클래스(`sm:` `md:` `lg:`)가
17군데뿐이다. 그중 6개는 shadcn 기본값이고, 나머지 11개는 최근 며칠 사이
등록 폼과 목록을 손보며 들어간 것이다.

즉 **이 앱은 모바일을 고려하고 만들어진 적이 없다.** 데스크톱 앱이 폰에서도
그냥 그려지고 있을 뿐이다. TopBar 잘림은 증상이지 원인이 아니다.

`viewport` 메타 태그는 정상이다(Next.js App Router 기본값으로
`width=device-width, initial-scale=1` 이 들어간다). 잘리는 것은 순전히
레이아웃 넘침이다.

## 목표와 범위

모바일 사용자는 **브랜드 요청자(4차 온라인 MD)** 로 잡는다.

이들이 폰에서 하는 일은 넷이다 — 요구사항 등록, 내 요청 확인, 알림 확인,
코멘트. IT 실무(보드 드래그·중복 병합·승인)는 데스크톱 전제다.

이 결정이 아래 모든 판단의 기준이 된다. 어떤 화면에 얼마나 공을 들일지는
"요청자가 폰에서 이 화면을 만나는가"로 정한다.

### 이번에 하지 않는 것

- **다크 모드** — 전 화면 색 재정의라 이 사이클과 크기가 맞지 않는다
- **PWA · 홈 화면 추가 · 앱 푸시** — 별개 사이클
- **보드의 모바일 대체 뷰** — 아래 C 항목 참조
- **관리 화면의 모바일 카드 뷰** — 아래 B 항목 참조
- **`RequirementDetail` 분할** — 910줄이라 부담스럽지만 이번에 건드리는 것은
  최상단 grid 구조뿐이다. 지금 쪼개면 모바일 작업과 리팩터링이 한 커밋에
  섞인다

### 공통 전제

- 마이그레이션 없음. API 변경 없음. 전부 화면 계층이다.
- 화면을 모바일용·데스크톱용 두 벌로 만들지 않는다. 같은 컴포넌트 안에서
  `md:` 로 갈린다. 두 벌이 되면 필드가 늘 때마다 두 곳을 고쳐야 하고 언젠가
  한쪽만 고친다 — 이 프로젝트에서 이미 겪었다(유형을 목록·보드에 넣고
  상세를 빠뜨렸다).
- 분기점은 `md`(768px)를 기본으로 한다. 이미 `RequirementList` 가 표/카드를
  `md` 에서 가르고 있으므로 새 기준을 만들지 않는다. 등록 폼의 2열 배치는
  `sm` 으로 되어 있는데 **그대로 둔다** — 태블릿 세로에서 2열이 잘 보이는
  것은 의도한 것이고, 지금 `md` 로 바꾸면 이번 작업과 무관한 데스크톱 회귀가
  섞인다.

## 1. 공통 뼈대

### 1.1 TopBar

현재 한 줄 `flex` 에 왼쪽 7개(모아 MOA · 구분선 · 브랜드 · 요구사항 ·
구분선 · 프로젝트 · 대시보드), 오른쪽 3개(벨 · 이름 · 아바타)가 들어 있고
간격이 20px씩이다. 375px 화면에서 쓸 수 있는 폭은 343px인데 내용은 그
1.4배쯤 된다. 줄바꿈도 가로 스크롤도 없으니 오른쪽이 잘려 나간다.

**모바일(< md)**

```
[모아 · 스파오]                    [벨] [아바타]
```

- 브랜드는 **텍스트로만 표시하고 전환은 막는다.** 브랜드가 여럿인 사람은
  전체관리자뿐이고 그 사람은 데스크톱에서 일한다. 다만 **표시는 반드시
  남긴다** — 어느 브랜드를 보고 있는지 모르는 것이 가장 위험하다.
- `요구사항` · `프로젝트` · `대시보드` 링크는 아바타 메뉴 안으로 들어간다.
  메뉴에는 이미 설정 · 브랜드 관리 · 팀원 관리 · 도움말 · 비밀번호 변경 ·
  로그아웃이 있으므로 자리는 있다.
- 아바타 메뉴는 현재 `w-44` 드롭다운이다. 모바일에서는 화면 폭에 맞춘
  시트로 열고 항목 높이를 44px로 올린다. 지금 `py-1.5`(30px)로는 터치
  타깃이 모자란다.

**데스크톱(≥ md)**: 지금 그대로. 바뀌지 않는다.

### 1.2 플로팅 등록 버튼

- 오른쪽 아래 고정, 56px 원형, `+` 아이콘
- **요구사항 목록에서만** 뜬다. 다른 화면에 띄우면 "여기서 뭘 등록한다는
  거지"가 된다
- 목록 컨테이너에 `pb-20` 을 줘서 마지막 카드가 가리지 않게 한다

### 1.3 터치 타깃

앱 전체가 `h-8`(32px) 기준이다. 데스크톱에서는 적당하지만 손가락에는 작다.
**모바일에서만** 주요 컨트롤을 44px로 올린다 — 버튼 · 셀렉트 · 입력 ·
메뉴 항목.

표 안의 인라인 셀렉트는 해당 없다(모바일에 표가 없다).

## 2. 요구사항 목록

### 2.1 카드 재설계

현재 모바일 카드의 마지막 줄은 이렇다.

```
미분류 · 자사몰 · 미분류 · 한지웅 08-20 예정 결제개편 📎2 미연결
```

값 6~9개를 `·` 로 이어 붙였다. 375px에서 3~4줄로 감기는데 감기는 위치가
데이터마다 달라 카드마다 높이와 모양이 제각각이다. `Meta` 가 `inline-flex`
인데 부모도 `flex` 라 줄바꿈이 예측 불가능한 것도 겹친다.

더 큰 문제는 **담당자가 없다**는 것이다. 요청자가 폰을 꺼내 보는 이유는
하나 — "내 요청 어디까지 왔나". 그 답은 상태 · 담당자 · 예상일인데 담당자가
안 보인다.

**새 구조 — 4줄 고정**

| 줄 | 내용 | 정렬 |
|---|---|---|
| 1 | 상태 배지 / 예상·완료일 | `justify-between` |
| 2 | 제목 | 2줄까지, 넘치면 말줄임 |
| 3 | 유형 · 채널 / `담당 ○○○` | `justify-between` |
| 4 | `○○○ 요청` · 첨부 · 프로젝트 · 미연결 | 왼쪽 정렬, 11px 회색 |

- 담당자가 없으면 `담당 미지정`. 표에서는 빈 값을 `—` 로 통일했지만
  카드에서는 라벨을 붙인다. **표는 헤더가 라벨 역할을 하지만 카드는 헤더가
  없다.** `—` 하나만 떠 있으면 그것이 담당자 자리인지 알 수 없다. 통일
  원칙을 어기는 것이 아니라 맥락이 다르다.
- **카테고리는 뺀다.** 대부분 `미분류` 라 자리만 먹는다.
- **요청자는 항상 4번째 줄에 표시한다.** 검토 과정에서 "내가 아닐 때만
  표시"를 고려했다가 버렸다. 이유가 셋이다.
  1. 없다는 것이 뜻을 갖는데 그 규칙이 화면 어디에도 없다. 빈칸이 뜻을
     가지면 안 된다는 것이 `—` 통일의 이유였는데 정반대가 된다.
  2. 3번째 줄에 놓을 자리가 없다. 375px에서 `오류 · 자사몰` +
     `담당 박실무` 만으로 이미 꽉 찬다.
  3. 이득 보는 사람이 거의 없다. 남의 요청과 섞여 보이는 사람은 IT(데스크톱
     사용)와 브랜드 관리자인데, 브랜드 관리자는 카드 대부분이 남의 요청이라
     조건부의 이득이 사라진다.

  요청자는 항상 있으므로 4번째 줄도 항상 생긴다. 결과적으로 **카드 높이가
  완전히 균일해진다** — 지금 가장 큰 불만이 제각각인 높이였으므로 이쪽이
  낫다.

### 2.2 필터

현재 375px에서 검색창(`w-48`, 192px) + 상태 + 유형이 2~3줄, 그 아래
체크박스가 또 2줄로 **화면 위 120px를 필터가 먹는다.** 요구사항은 9건이다.

**모바일**: 한 줄로 줄인다.

```
[제목 검색                    ] [필터 2]
```

`필터` 를 누르면 하단 시트가 올라오고 그 안에 나머지 전부가 들어간다 —
상태 · 유형 · 담당자 · 카테고리 · 채널 · 우선순위 · 프로젝트 + 체크박스 2개
(종결 숨김, 내 요청만).

적용 중인 필터 개수를 버튼에 숫자로 붙인다. **보이지 않는 필터가 제일
나쁘다** — 결과가 좁아진 이유가 화면 어디에도 없으면 사용자는 목록이 고장난
줄 안다. 데스크톱의 `필터 더보기 (N)` 와 같은 원칙이다.

시트는 **새 컴포넌트 파일 하나(`FilterSheet.jsx`)로 만들되, 내부는 기존
`Dialog` 를 그대로 쓴다.** 새 오버레이 메커니즘을 만들지 않는다는 뜻이다 —
모바일에서 `sm:max-w-*` 가 안 걸리면 `Dialog` 는 이미 화면을 거의 채운다.

필터 컨트롤 자체는 `FilterBar` 가 이미 갖고 있으므로, 시트는 그 컨트롤들을
받아 세로로 배치하는 껍데기다. 선택지 목록을 두 곳에 복제하지 않는다.

**데스크톱**: 지금의 접기/펼치기 그대로.

### 2.3 페이지 헤더

모바일에서 이 줄을 통째로 없앤다.

| 요소 | 근거 |
|---|---|
| `+ 새 요구사항` | 플로팅 버튼으로 갔으므로 중복 |
| `CSV` | 폰에서 받아도 열 데가 없다 |
| `목록 / 보드` 토글 | 보드는 3차+ 전용이고 드래그라 폰에서 못 쓴다 |
| `요구사항 목록` 제목 | TopBar에 `모아 · 스파오` 가 있고 화면이 사실상 하나라 자명하다 |

세로 40px를 벌고, 첫 화면에 카드가 한 장 더 들어온다.

## 3. 등록 폼과 상세

### 3.1 등록 폼 — 에러 위치 (실제 버그)

에러 메시지가 `<form>` 맨 위에 있다. 모바일에서 폼을 다 내려가 아래쪽
`검토 요청` 을 눌렀는데 채널을 안 골랐다면 **에러는 화면 밖 저 위에 뜬다.**
사용자 눈에는 버튼을 눌렀는데 아무 일도 안 일어난 것으로 보인다.

어제 채널을 필수로 만들면서 이 경로를 새로 만들어 놓고 보지 못했다.

**에러를 `DialogFooter` 바로 위로 옮긴다.** 누른 사람의 눈은 버튼 근처에
있다. 데스크톱에서도 이쪽이 맞다.

### 3.2 등록 폼 — 오른쪽 열 순서

현재 `유형 → 우선순위+채널 → 카테고리+요청일 → 프로젝트` 다. **필수값인
채널이 두 번째 줄**에 있고 그 위의 유형은 필수가 아니다.

바꾼다: `채널*+유형 → 우선순위+카테고리 → 요청일+프로젝트`

모바일에서 세로로 떨어질 때도 필수가 먼저 나온다.

### 3.3 등록 폼 — 유형 안내 박스

4줄짜리 설명 박스가 모바일 화면의 3분의 1을 먹는다. 모바일에서는
`유형이 뭔가요?` 링크로 접어 두고 누르면 펼친다. 데스크톱은 지금처럼
펼친 채로 — 자리가 있다.

### 3.4 등록 폼 — 첨부 문구

현재 문구는 이렇다.

> 파일을 드래그하거나 클릭해서 선택 · 스크린샷은 Ctrl+V로 붙여넣기

**폰에는 드래그도 Ctrl+V도 없다.** 모바일에서는 `사진·파일 선택` 으로
바꾼다.

### 3.5 등록 폼 — 버튼

모바일에서 `임시저장` / `검토 요청` 을 44px 높이로, 가로 꽉 채워 세로
스택. 지금 `sm:flex-row` 라 세로로 떨어지기는 하는데 높이가 32px다.

### 3.6 상세 화면 — 순서

현재 구조는 `grid-cols-1 md:grid-cols-3` 안에 본문(`md:col-span-2`)과
메타(`aside`)가 있고, 코멘트·이력은 grid 밖 아래에 있다. 모바일에서는
`본문 → 메타 → 코멘트` 순서로 떨어진다.

코멘트보다 메타가 위인 것은 다행이지만, **본문 전체(제목·As-Is·To-Be·
비고·첨부)를 지나야 상태가 나온다.** 폰으로 상세를 여는 이유가 "어디까지
왔나"인데 그것이 화면 밖이다.

**제목을 grid 밖으로 빼서 항상 맨 위에 두고, 모바일에서 메타를 본문 위로
올린다.**

```
제목                          [수정]     ← grid 밖
┌──────────────────┬──────────────┐
│ As-Is / To-Be    │ 상태          │      데스크톱: 지금 그대로
│ 비고 / 첨부      │ 담당자        │
│                  │ 예상일        │
└──────────────────┴──────────────┘
코멘트 · 이력
```

모바일 순서: 제목 → 상태·담당자·예상일·(승인 버튼) → 본문 → 코멘트

`order-first md:order-none` 클래스 하나로 처리한다.

### 3.7 상세 화면 — 터치 타깃

상태 Select, 담당자 Select, 승인 버튼을 모바일에서 44px로. 특히
`승인하고 완료` 는 되돌리기 어려운 동작이라 잘못 누르면 안 되고,
**작으면 오히려 잘못 누른다.**

## 4. 나머지 화면

### A. 제대로 손볼 것 — 요청자가 폰에서 만나는 화면

**로그인 · 가입 · 비밀번호 변경**

구조는 이미 괜찮다 — `w-full max-w-sm` 이라 폰에서 자연스럽게 채워진다.
**첫 접속이 폰일 수 있으므로 여기가 깨지면 앱을 못 쓴다.** 입력·버튼을
44px로 올리는 것만 한다.

**도움말 `/help`**

`StatusGuide` · `TierGuide` 두 표가 있다. **권한이 가장 낮은 요청자가 가장
자주 보는 화면**인데(상태 뜻, 등급 뜻) 표라서 폰에서 밀린다. 모바일에서는
표 대신 항목별 정의 목록으로 떨어뜨린다.

**알림 패널**

`w-80`(320px)이라 375px 화면에 겨우 들어가고 더 좁은 폰에서는 넘친다.
모바일에서 화면 폭에 맞춘다.

### B. 깨지지만 않게 — 표를 가로 스크롤로

대상: `/projects`, `/admin/dashboard`, `/requirements/settings`,
`/admin/brands`, `/admin/members`

관련 컴포넌트: `BrandListSection`, `BrandTeamSection`,
`PendingMembersSection`, `TeamMemberListSection`, 그리고 `/projects` 와
`/admin/dashboard` 페이지 안의 표.

표 7개가 대안 없이 그대로 있다. 모바일 카드 뷰를 만드는 것은 **이 화면들에
그럴 가치가 없다** — 관리 화면은 데스크톱에서 쓴다.

**공통 조치**: 각 표를 `overflow-x-auto` 래퍼로 감싼다. 표는 옆으로
스크롤되고 페이지 전체는 밀리지 않는다. 이것이 "깨진 화면"과 "좁은 화면"의
차이다.

`RoadmapView` 는 이미 `overflow-x-auto` 가 있어 손댈 것이 없다.

### C. 안내로 대체

**보드 `/requirements/board`**

컬럼 7개 × 180px = 1260px에 드래그 앤 드롭이다. 폰에서 드래그는 스크롤
제스처와 충돌해 사실상 불가능하다.

모바일에서 뷰 토글을 숨기므로 **보드로 갈 길 자체가 없다.** URL을 직접
열었을 때만 도달하므로, 그 경우 안내 한 줄과 목록으로 가는 링크를 띄운다.
모바일용 대체 보드는 만들지 않는다.

## 검증

이 사이클은 순수 화면 작업이라 단위 테스트로 잡히는 것이 거의 없다.
검증은 다음 셋으로 한다.

1. `npm run lint` 0 errors, 기존 테스트 467개 유지, `npm run build` 성공
2. 배포 후 실제 폰에서 확인. 확인 항목:
   - TopBar가 잘리지 않는가 (375px, 320px 둘 다)
   - 어느 브랜드를 보고 있는지 보이는가
   - 플로팅 버튼이 마지막 카드를 가리지 않는가
   - 카드 높이가 균일한가
   - 필터 시트가 열리고 적용 개수가 버튼에 뜨는가
   - 채널을 비우고 제출했을 때 **에러가 화면 안에 뜨는가**
   - 상세에서 상태·담당자가 첫 화면에 보이는가
   - 관리 화면에서 페이지 전체가 아니라 표만 옆으로 스크롤되는가
3. 데스크톱 회귀 확인 — 이 작업의 대부분이 `md:` 분기 추가이므로 데스크톱
   화면이 그대로여야 한다. 특히 TopBar, 등록 폼 2열, 목록 표.
