# 회의 중심 재설계 설계

목요일 주간회의를 MOA 의 중심에 놓는다. 수요일에 회의 안건을 메일로 보내고,
회의에서는 전용 화면으로 담당자와 예상일을 정하고, 그 결과를 요청자에게
돌려준다.

작성일 2026-08-26

---

## 왜 지금인가

운영 2주 시점에 실제 데이터를 봤다. 추측이 아니라 여기서 출발한다.

**1. 절반 이상이 고여 있다.** 요구사항 41건 중 검토대기가 22건(54%). 미완료
38건 중 16건은 마지막 변경 이후 20일이 지났다. 8/5 에 올라온 것들이 지금까지
손도 닿지 않았다 — 타임세일, 사은품 기능 업데이트, 품절 상품 리스팅 정렬,
장바구니 최대혜택가. 담당자가 지정된 건은 41건 중 13건(32%)뿐이고, 완료는
3건이다.

**2. 그 사실을 아무도 모른다.** 인앱 알림 110건 중 105건(95%)이 안 읽혔다.
종 아이콘을 아무도 보지 않는다. 화면 어디에도 "이 건은 20일째 멈췄다"가
뜨지 않는다.

**3. 사람이 돌아오지 않는다.** 활성 19명 중 13명이 일주일 넘게 로그인하지
않았다. 가장 많이 올린 세 사람(10건·5건·4건)은 26일째 들어오지 않았다. 자기가
올린 것이 어떻게 됐는지 확인하러 오지 않는다는 뜻이다.

**4. 일은 앱 밖에서 굴러간다.** 사내에서 매일 보는 디지털 통로는 메일뿐이고,
실제 진행은 주간회의와 구두로 이뤄진다. 앱은 그 자리 바깥에 따로 서 있다.

정리하면 루프가 한 바퀴를 못 돈다 — **올린다 → 아무 일도 안 일어난다 → 다시
안 온다.**

### 이 설계가 풀지 않는 것

담당 라인이 아직 없다. 배치 32건이 2차 11 / 3차 1 / 4차 20 으로, 요청을 받아
처리하는 실무자가 사실상 1명이다. 이건 조직의 문제이지 화면의 문제가 아니다.

그래서 "담당자 없이는 상태를 못 옮긴다" 같은 강제는 넣지 않는다. 배정할 사람이
없는 상태에서 그런 벽을 세우면 22건이 검토대기에서 못 나가는 대신 접수 자체가
막힌다. 대신 **담당 없음을 드러내고, 회의라는 자리로 밀어 넣는 것**까지가 이
설계의 몫이다.

## 1. 담당자 변경을 로그에서 구분한다

**먼저 고쳐야 하는 것이다.** 지금은 담당자를 바꿔도 `change_logs` 에
`change_type='내용수정'`, `comment='담당자 수정'` 으로만 남는다. `field_name`
이 비어 있어서 "이 회의에서 배정된 건"을 찾을 방법이 없다. 실제 운영 로그
72건 중 34건이 이 뭉뚱그려진 '내용수정'이다.

`app/api/requirements/[id]/route.js` 의 PATCH 에서 담당자 변경만 떼어 별도
로그로 남긴다.

```
change_type: '담당자지정'
field_name:  'assignee'
old_value:   이전 담당자 이름 (없으면 null)
new_value:   새 담당자 이름 (해제면 null)
```

**왜 담당자만 특별 취급하는가.** 다른 필드까지 전부 쪼개면 감사 기록 구조를
바꾸는 일이 되고, 한 번의 수정이 로그 여러 줄로 흩어진다. 담당자는 이 앱에서
성격이 다르다 — 정체의 원인이자 회의의 산출물이다. 예상일이 이미
`change_type='예상일변경'` 으로 따로 나가 있는 것과 같은 이유다.

곁가지 이득이 하나 있다. 활동 피드에 지금은 "담당자 수정"이라고만 뜨는데,
"담당자를 장재혁으로 지정"으로 바뀐다.

**기존 34건은 그대로 둔다.** 옛 로그를 고쳐 쓰지 않는 것이 이 프로젝트의
규칙이고(0007 상태명 변경 때 정한 것), 회의 기능은 첫 회의 시점부터의 로그만
보므로 과거 데이터가 필요 없다.

## 2. 정체 판정 — `lib/stalled.js`

순수 함수. 요구사항 하나가 얼마나 멈춰 있는지 계산한다.

```js
export const STALL_DAYS = 14;

// 마지막으로 무언가 일어난 시각.
lastActivityAt({ requirement, changeLogs, comments }) -> ISO string

// 그로부터 며칠 지났나. 종결 건은 null.
stalledDays({ requirement, changeLogs, comments, now }) -> number | null
```

**마지막 활동은 세 곳을 본다.** `requirements.created_at`, 그 건의 마지막
`change_logs.created_at`, 그리고 마지막 `requirement_comments.created_at` 중
가장 나중 것. 코멘트를 빼면 안 된다 — 운영 로그에 코멘트가 42건 달려 있고,
논의가 활발한 건이 "아무도 안 건드린 건"으로 잡히면 안건이 오염된다.

**종결 건은 정체가 아니다.** `CLOSED_STATUSES`(완료·반려·취소·중복)는 `null`
을 돌려준다. 멈춘 게 아니라 끝난 것이다. 실제로 지금 20일 넘은 16건 중 3건이
반려·중복이라, 이 규칙 하나로 안건이 13건으로 줄어든다.

**14일인 이유.** 7일로 잡으면 미완료 38건 중 27건이 걸려 안건이 아니라 목록이
된다. 14일은 "회의를 이미 한 번 그냥 지나쳤다"는 뜻이라 안건 자격이 있고,
실데이터에서 13건이 나온다 — 한 시간짜리 회의가 다룰 수 있는 크기다.

상수로 둔다. 회의가 자리 잡으면 조정할 값이다.

## 3. 회의 메일 — `lib/meetingDigest.js`

순수 함수 하나가 메일 내용을 만든다. 발송은 `lib/notify.js` 가 한다 — 기존
주간 요약과 같은 구조다.

```js
buildMeetingDigest({ requirements, changeLogs, comments, today })
  -> { hasContent, stalled, incoming, moved }
```

세 블록이다.

**① 멈춘 것** — `stalledDays >= 14` 인 미종결 건. 정렬은 **담당 없는 것 먼저,
그 안에서 오래 멈춘 순**. 담당이 없으면 예상일도 티켓도 나올 수 없으니 회의가
먼저 손대야 할 것이 그쪽이다.

**② 이번 주 새로 들어온 것** — 지난 7일 `created_at`.

**③ 이번 주 움직인 것** — 지난 7일 안에 상태가 바뀐 건. `change_logs` 에서
`field_name='status'` 로 거른다. `change_type` 으로 거르면 안 된다 — 상태
변경은 `'상태변경'` 과 `'중복병합'` 두 종류를 쓴다(`lib/statusDurations.js` 의
같은 주석 참고).

각 블록은 상위 5건을 제목으로 펴고 나머지는 "외 N건"으로 접는다. 기존
`weeklyDigest` 의 `TOP_N` 과 같은 값이고 같은 이유다 — 25건을 전부 펴면 그건
목록이지 안건이 아니다.

**블록 간 중복 제거는 하지 않는다.** 주간 요약에서는 세 섹션의 상위 5건이
글자까지 똑같이 나오는 문제가 있어 `seen` 으로 걸렀다. 여기서는 세 블록이
성격상 겹치지 않는다 — 이번 주 들어온 건이 14일 멈춰 있을 수 없고, 이번 주
움직인 건도 마찬가지다.

**보낼 값어치.** `hasContent` 는 ①이나 ②가 있을 때 참이다. ③만 있는 주는
잘 굴러간 주라서 안건이 없다. 안건 없는 메일이 오기 시작하면 정작 밀린 주에도
안 열린다.

### 수신자와 발송

`sendMeetingDigest()` 가 브랜드별로 돌면서 **그 브랜드 3차 이상**에게 보낸다.
기존 `sendWeeklyDigest` 의 수신자 계산을 그대로 쓴다. 회의 참석자가 곧 실무
관리자(2차)와 실무자(3차)라 범위가 같다.

**개인화는 하지 않는다.** 주간 요약은 맨 위에 "회원님 담당 중 지연"을 두었는데,
회의 메일은 같은 자료를 같이 보고 논의하는 것이라 사람마다 다르면 회의에서
"제 메일에는 그게 없는데요"가 나온다.

### 크론

`app/api/cron/meeting-digest/route.js`. 기존 `weekly-digest` 라우트를 그대로
본뜬다 — POST, `CRON_SECRET` 없으면 503, `Authorization: Bearer` 와
`x-noa-token` 둘 다 받는다(배포 플랫폼 스케줄러는 헤더 이름이 고정이다).

스케줄은 **수요일 오후**. 배포 플랫폼의 배치/스케줄 화면에서 등록한다.

**월요일 주간 요약 스케줄은 지운다.** 코드(`lib/weeklyDigest.js`,
`/api/cron/weekly-digest`)는 남긴다 — 되돌리고 싶으면 스케줄만 다시 걸면
된다. 둘 다 두면 같은 목록이 주 2회 오고, 그러면 둘 다 안 읽힌다.

## 4. `/meeting` 페이지

`app/meeting/page.jsx` + `components/MeetingBoard.jsx`.

**새 페이지로 만든다.** 목록 페이지에 '회의 모드' 버튼을 다는 안도 있었지만,
목적이 분명한 주소여야 메일 링크가 바로 꽂히고 처음 보는 사람도 이 화면이 무슨
자리인지 안다.

### 구성

```
주간회의 · 스파오
2026-08-27

[14일+ 멈춤 13]  [담당 없음 28]  [이번 주 신규 3]

보기  (오래 멈춘 순) (담당 없는 것만) (이번 주 신규)
─────────────────────────────────────────────────
│ 브레이즈 고도화
│ [22일 멈춤]  검토대기 · 박천주 요청    [담당 지정▾] [예상일]
─────────────────────────────────────────────────
│ 타임세일
│ [20일 멈춤]  검토대기 · 박천주 요청    [담당 지정▾] [예상일]
─────────────────────────────────────────────────
        ...
이 회의에서 3건 배정 · 2건 예상일 지정        [회의 마치기]
```

빨간 왼쪽 테두리는 담당자가 없는 행이다.

### 데이터

`GET /api/meeting?brandId=` 하나가 화면에 필요한 걸 다 준다.

```
{
  summary: { stalled, unassigned, incoming },
  rows: [{ id, title, status, stalledDays, requester, assignee, expectedDate }]
}
```

미종결 건 전부를 `stalledDays` 내림차순으로 준다. 필터 세 개는 클라이언트에서
건다 — 회의 중에 왔다 갔다 하는 조작이라 왕복이 없어야 한다.

브랜드가 여럿인 관리자에게는 브랜드 셀렉트를 준다. 기본값은 본인 브랜드다.

### 인라인 저장

담당자는 기존 `PATCH /api/requirements/[id]`, 예상일은 기존
`PATCH /api/requirements/[id]/expected-date` 를 그대로 부른다. **새 엔드포인트를
만들지 않는다** — 권한 검사와 로그 기록이 이미 그 안에 있고, 회의용으로 따로
만들면 두 길이 갈라져서 한쪽만 고쳐지는 날이 온다.

저장은 셀렉트를 바꾸는 즉시. 실패하면 그 행에만 붉은 문구를 띄우고 값을
되돌린다. 회의 중이라 저장 버튼을 따로 누르게 하면 안 누른 채 넘어간다.

### 권한

3차 이상(`canProcess`). 4차(요청자)는 담당자를 지정할 수 없으므로 이 화면에
들어올 이유가 없다. 접근하면 목록 페이지로 보낸다.

## 5. 회의 마치기 → 요청자에게

루프를 닫는 지점이다. 26일째 안 들어온 사람들이 돌아올 유일한 고리다.

### `meeting_sessions` 테이블 (마이그레이션 0024)

```sql
create table meeting_sessions (
  id uuid primary key default gen_random_uuid(),
  brand_id uuid not null references brands(id),
  ended_at timestamptz not null default now(),
  ended_by uuid references team_members(id)
);
create index idx_meeting_sessions_brand on meeting_sessions (brand_id, ended_at desc);
```

시작 시각은 두지 않는다. "직전 회의가 끝난 뒤부터 지금까지"만 알면 되고,
시작을 기록하려면 회의 화면을 여는 것이 곧 회의 시작이라고 정해야 하는데
화면은 회의 밖에서도 열린다.

### `POST /api/meeting/end`

1. 그 브랜드의 마지막 `ended_at` 을 찾는다. 없으면 7일 전으로 본다(첫 회의).
2. 그 이후 `change_type='담당자지정'` 이고 `new_value` 가 있는 로그를 모은다.
3. 해당 요구사항들을 **요청자별로 묶는다.**
4. 요청자마다 메일 한 통 + 인앱 알림 한 건.
5. `meeting_sessions` 에 한 줄 넣는다.

**왜 묶는가.** 건별 즉시 발송이면 10건을 올린 사람이 회의 한 번에 10통을 받는다.
실제로 한 사람이 10건, 다른 한 사람이 5건을 올렸다.

메일 문구:

> **올리신 요구사항 2건에 담당자가 정해졌습니다**
>
> 타임세일 — 담당 장재혁, 예상 9/15
> 사은품 기능 업데이트 — 담당 안수아
>
> MOA 에서 열기

인앱 알림도 같이 남긴다. 지금 95% 가 안 읽히는 통로라 기대하지는 않지만, 메일이
막힌 사람에게는 그것뿐이다.

**보낼 것이 없으면 그냥 세션만 닫는다.** 배정이 0건인 회의도 있고, 그때 "0건이
배정되었습니다" 메일이 나가면 안 된다.

`lib/meetingSession.js` 에 순수 함수로 뺀다.

```js
groupAssignmentsByRequester({ assignmentLogs, requirements })
  -> [{ requesterId, items: [{ id, title, assigneeName, expectedDate }] }]
```

## 테스트

순수 함수 셋이 핵심이다. 나머지는 기존 패턴을 따른다.

**`lib/stalled.test.js`**
- 마지막 활동이 change_logs 인 경우 / comments 인 경우 / 둘 다 없어 created_at 인 경우

## 오류 처리

- 메일 발송 실패는 화면을 막지 않는다. `lib/notify.js` 의 함수들은 던지지 않고
  결과를 돌려준다는 규약이 이미 있다.
- 회의 마치기에서 세션 기록은 되고 메일이 실패한 경우, 세션은 닫힌 것으로 둔다.
  다시 누르면 직전 세션 이후로 계산되어 아무것도 안 나가는 것이 맞다 — 같은
  메일을 두 번 받는 쪽이 더 나쁘다.
- 크론 시크릿 미설정은 503. 기존과 같다.

## 범위 밖

**긴급도·스크린샷 정리** — 운영 데이터에서 41건 전부 비어 있어 없애려 했으나,
확인해 보니 `screenshot_url` 은 코드 어디에서도 참조되지 않고(이미지 업로드로
대체됨) `urgency` 는 API 만 받고 입력 폼에 칸이 없다. 사람들이 안 쓴 게 아니라
채울 곳이 없었다. 할 일이 없다.

**미쏘** — 8명이 배치돼 있는데 요구사항 0건이다. 실제로 쓸 계획인지 아직 몰라
감추지 않는다.

**담당자 필수화** — 위 "이 설계가 풀지 않는 것" 참고. 담당 라인이 생긴 뒤에
다시 볼 일이다.

**회의록 내보내기** — 목업에는 버튼이 있었지만 넣지 않는다. 누르면 아무 일도
안 일어나는 버튼은 없는 것보다 나쁘다. 회의가 두어 번 돌아 무엇이 회의록에
필요한지 보인 뒤에 만든다.
