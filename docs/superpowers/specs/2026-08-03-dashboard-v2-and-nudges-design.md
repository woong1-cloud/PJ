# 대시보드 v2 + 담당자·예상일 유도 설계

**작성일:** 2026-08-03
**대상:** 모아 MOA
**버전:** v1.5

## 왜 지금 이것인가

배포 후 실제 데이터를 조회한 결과가 이 설계의 근거다.

```
전체 요구사항 9건 (전부 스파오)
  검토대기 6 · 작성중 2 · 반려 1
  담당자 미지정 8/8 · 예상일 미지정 8/8
  코멘트 0 · 하위 작업 0 · 프로젝트 0

브랜드 참여
  스파오    요구사항 9  배치 팀원 6
  미쏘      요구사항 0  배치 팀원 1
  로엠      요구사항 0  배치 팀원 1
  후아유    요구사항 0  배치 팀원 1
  뉴발란스  요구사항 0  배치 팀원 0
```

두 가지가 드러난다.

1. **앞단이 막혀 있다.** 브랜드는 올렸는데 IT가 아직 아무것도 집지 않았다.
   담당자·예상일이 8/8로 비어 있어 지연 판정·로드맵·대시보드가 전부 죽어 있다.
2. **멀티브랜드 툴인데 브랜드 하나만 쓴다.** 그런데 지금 대시보드는 이것을
   "0이 네 줄"로만 보여준다.

그래서 새 기능을 더 만드는 대신, **이미 있는 것이 돌아가게 만드는 것**이 이번
범위다. 마이그레이션은 없다.

## A. 착수 다이얼로그

`검토대기 → 검토중` 으로 옮기는 순간에 담당자와 예상 배포일을 묻는다.

**이 순간인 이유:** 등록 시점에는 브랜드가 두 값을 알 수 없다. IT가 정하는
값이고, IT가 그 건을 처음 손대는 순간이 `검토중` 으로 옮길 때다.

**`나중에 정하기` 버튼을 둔다.** 필수로 막으면 급할 때 사람들이 상태를 아예
안 옮기고 그냥 일해 버린다 — 그러면 보드가 현실과 어긋나고, 그게 이런 툴이
죽는 가장 흔한 방식이다. 막지 않되 기본값을 "채우는 쪽"으로 둔다.

`검토중` 으로 갈 때만 뜬다. 나머지 전환은 지금처럼 즉시 반영된다.

### 저장 방식

새 라우트를 만들지 않는다. 이미 있는 세 라우트를 순서대로 부른다.

1. `PATCH .../assignee` (담당자를 골랐을 때만)
2. `PATCH .../expected-date` (날짜를 넣었을 때만)
3. `PATCH .../status` → `검토중`

**상태를 마지막에 보낸다.** 앞의 둘이 실패하면 카드가 움직이지 않아서, 사용자가
오류를 보고 다시 시도할 수 있다. 상태를 먼저 보내면 "옮겨는 갔는데 값은 안
들어간" 상태가 조용히 남는다.

각 라우트가 자기 `change_logs` 를 남기므로 이력은 세 줄이 된다. 실제로 세 가지가
바뀌었으므로 맞는 기록이다.

## B. 손볼 것

대시보드 최상단. 관리자가 **눌러서 갈 곳**만 모은다.

| 항목 | 조건 | 링크 |
|---|---|---|
| 담당자 없는 검토대기 | `status=검토대기` 이고 `assignee` 가 비어 있음 | `/requirements?status=검토대기&missing=assignee` |
| 예상일 없는 진행 건 | 미종결이고 `expected_release_date` 가 비어 있음 | `/requirements?missing=expectedDate` |
| 팀원 없는 브랜드 | `user_brand_roles` 행이 0인 활성 브랜드 | `/admin/brands` |

**0인 항목은 줄 자체를 감춘다.** 다만 셋 다 0이면 "지금 손볼 것이 없습니다"를
보여준다 — 빈 화면은 "괜찮은 건지 안 불러와진 건지" 알 수 없다.

`팀원 없는 브랜드`가 목록에 있는 것이 중요하다. 그 브랜드는 계정이 없으므로
**가입 알림조차 오지 않는다.** 아무도 알려주지 않으면 영원히 모른다.

### 새 필터 파라미터

`missing=assignee|expectedDate` 하나를 추가한다.

```
missing=assignee      → .is('assignee', null)
missing=expectedDate  → .is('expected_release_date', null)
```

`assignee=none` 처럼 기존 파라미터에 특수값을 넣지 않는다. 그러면 uuid 자리에
매직 문자열이 섞여서, 나중에 `none` 이라는 이름의 팀원이 생기면(없겠지만) 규칙이
무너진다. 별도 파라미터가 의도도 분명하다.

`missing` 은 `FILTER_KEYS` 에 넣지 않는다 — 필터바에 노출하는 값이 아니라
대시보드에서 링크로만 들어오는 값이다. 필터바에 칸을 하나 더 만들면 평소에
아무도 안 쓰는 셀렉트가 하나 더 생긴다.

## C. 대시보드 재배치

위에서 아래로: **손볼 것 → 브랜드 도입 → 지금 어디에 있나 → 브랜드별 지표 →
프로젝트**.

### 브랜드 도입

머리말에 `5개 중 1개 사용 중`. 브랜드마다 한 줄로 요구사항 수·배치 팀원 수와
막대 하나.

세 단계로 나눈다. 처방이 다르기 때문이다.

| 단계 | 조건 | 무엇을 해야 하나 |
|---|---|---|
| 사용 중 | 요구사항 ≥ 1 | 없음 |
| 배치만 됨 | 팀원 ≥ 1, 요구사항 0 | 독려 — 계정은 있는데 안 쓴다 |
| 시작 안 함 | 팀원 0 | 계정 발급 — 아무도 들어올 수 없다 |

### 지금 어디에 있나

`BOARD_STATUSES` 순서대로 상태별 건수를 막대로. 종결 상태(반려·취소·중복)는
빼서 흐름만 보이게 한다.

**건수가 가장 많은 칸을 강조한다.** 지금은 검토대기 6이고, 그게 병목이다.
브랜드가 늘고 건수가 쌓이면 이 그림이 매번 자동으로 병목을 가리킨다.

### 빈 지표

`평균 처리 기간`이 지금 `—` 로 떠 있다. 고장난 것처럼 보인다.

**숨기지 않고, 언제 나타나는지 말한다** — "평균 처리 기간은 완료 3건부터
표시됩니다." 숨기면 그런 지표가 있는 줄도 모르고, `—` 만 두면 버그로 본다.
도입 단계 툴에서는 이 문구 하나가 신뢰를 만든다.

`MIN_COMPLETED_FOR_AVG = 3`. 1~2건의 평균은 평균이라 부를 수 없다.

### 기존 것

브랜드별 카드(신규/완료/평균)와 프로젝트 섹션은 **버리지 않고 아래로 내린다.**
완료 건이 쌓이면 의미가 생긴다.

## 테스트

`lib/dashboardStats.test.js` 에 추가한다. 순수 함수라 전부 테스트 가능하다.

- `computeActionItems` — 0인 항목이 빠지는지, 셋 다 0이면 빈 배열인지
- `computeAdoption` — 사용중/배치만됨/시작안함 세 단계 판정
- `computeStatusFlow` — 종결 상태 제외, `BOARD_STATUSES` 순서 유지, 최대값 표시
- `MIN_COMPLETED_FOR_AVG` 미만이면 평균이 null 인지

라우트와 화면은 기존 관행대로 브라우저에서 확인한다.
