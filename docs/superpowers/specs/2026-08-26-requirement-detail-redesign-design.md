# 요구사항 상세 화면 재설계 설계

멈춘 건이 멈춰 보이게 하고, 실무자가 다음 한 걸음을 한 번에 누르게 만든다.
여기서 나온 조각을 디자인 시스템의 1차 승격 대상으로 삼는다.

작성일 2026-08-26
목업 https://claude.ai/code/artifact/f1506e44-bd35-47ef-8dd7-97408e358c29

---

## 왜 지금인가

상세 화면은 이 앱의 모든 문제가 만나는 자리다.

**1. 화면이 이 건의 가장 중요한 사실을 말하지 않는다.** 44건 중 24건이
검토대기이고 담당자가 지정된 건은 32%뿐이다. 상세를 열면 그 사실이 회색
드롭다운 셋으로만 표시된다. 요청자는 "그래서 되는 건가"를, 실무자는 "다음에
뭘 해야 하나"를 화면에서 읽을 수 없다.

**2. 상태를 바꾸는 길이 셀렉트 하나에 뭉쳐 있다.** 그 목록에는 성격이 다른
셋이 섞여 있다 — 즉시 반영되는 것, 창이 뜨는 것(착수·승인), 그리고 서버가
아예 거부하는 것(완료). 고를 수 있어 보이는데 다른 일이 일어난다.

**3. 판단 근거가 잘려 있다.** 첨부가 있는 7건은 대부분 화면 캡처인데,
80px 정사각형에 `object-cover`로 잘려 무엇이 찍혔는지 알 수 없다. 누르면
새 탭으로 나가서 본문과 대조할 수도 없다.

**4. 있는 정보가 아래에 묻혀 있다.** 상태별 소요일(`StatusDurations`)은 이미
계산해서 그리고 있는데 710번째 줄에 있다. 코멘트 42건은 이 앱에서 유일하게
살아 있는 협업 신호인데 화면 맨 끝이다.

### 이 설계가 풀지 않는 것

사람이 안 들어오는 문제는 화면이 풀 수 없다. 활성 19명 중 13명이 일주일 넘게
로그인하지 않았고, 그건 [회의 중심 재설계](2026-08-26-meeting-centric-design.md)가
메일로 푸는 쪽이다. 이 설계는 **들어온 사람이 화면 앞에서 막히지 않게** 하는
데까지다.

## 1. 머리 줄

제목 아래 한 줄이 이 건의 상태를 말한다.

```
● 검토대기   20일째 멈춤 · 담당자 없음 · 첨부 1 · 대화 3      [검토 시작] [⋯]
```

담는 것은 다섯이다. 상태(색 점 + 이름), 경과, 담당 유무, 첨부·대화 수,
그리고 주 행동.

**경과는 상황에 따라 다른 말을 한다.**

| 상황 | 문구 |
|---|---|
| 정체 14일 이상 | `20일째 멈춤` (붉게) |
| 그 밖의 미종결 | `오늘 접수` · `3일째` |
| 완료 | `8일 걸림` — 경과가 아니라 소요 |
| 예상일 지남 | 알약 `⚠ 예상일 9월 1일 지남` |
| 기밀 | 알약 `비공개` |

정체 일수는 `lib/stalled.js` 의 `stalledDays` 를 그대로 쓴다. 회의 화면과
같은 판정이어야 한다 — 회의 안건에 오른 건을 상세에서 열었을 때 다른 숫자가
보이면 둘 중 하나는 틀린 것이다.

**같은 컴포넌트가 사람에 따라 다르게 말한다.** 화면을 둘로 나누지 않는다.

| 보는 사람 | 문구 | 행동 |
|---|---|---|
| 3차 이상 | `담당자 없음` | `[검토 시작]` |
| 요청자(4차) | `담당자를 기다리고 있습니다` | `[요청 취소]` |
| 승인대기 · 담당자 본인 | `다른 사람의 승인을 기다립니다` | 없음 |
| 승인대기 · 그 외 | — | `[승인하고 완료]` |

## 2. 진행 스트립

머리 줄 아래 한 줄.

```
작성중 2일 › 검토대기 20일 › 검토중 › 개발중 › QA중 › 승인대기 › 완료
```

지난 구간은 소요일과 함께, 현재 구간은 강조, 앞으로는 흐리게.

데이터는 `computeStatusDurations` 가 이미 만든다. 새로 계산하지 않는다.

**구간 불명을 그대로 그린다.** 그 함수는 상태명을 못 믿을 때 `status: null`
을 돌려준다(0007 이전 이름이 이력에 남아 있거나 로그가 빠진 구간). 그때는
`구간 불명 N일` 로 표시한다 — 정직하게 비워 두는 것이 그 함수의 설계 의도이고,
화면이 임의로 메우면 그 의도가 무너진다.

모바일에서는 가로 스크롤로 두고 뒤쪽은 `…` 로 접는다. 일곱 칸을 375px 에
펴면 두 줄이 된다.

## 3. 상태 컨트롤 — 셀렉트에서 버튼 + 메뉴로

### 주 버튼은 `STATUS_META` 에서 나온다

`lib/statusMeta.js` 에 이미 `next`(다음 행동)가 있고, 그 값이 이 설계의 버튼과
정확히 같다 — `IT — 검토 시작`, `IT — 개발 착수`, `IT — QA 시작`,
`IT — 승인 요청`. 워크플로 정의는 이미 이렇게 되어 있었고 화면만 따라가지
않고 있었다.

그래서 새 상수를 만들지 않고 `STATUS_META` 에 `primary` 를 더한다.

```js
primary: { label: '검토 시작', to: '검토중', via: 'start' }
```

`via` 는 누르면 무엇이 일어나는지를 말한다.

| 값 | 무엇이 |
|---|---|
| `'direct'` | `PATCH /status` 로 바로 |
| `'start'` | 착수 창(`StartReviewDialog`) |
| `'approve'` | 승인 창(`ApprovalDialog`) |
| `'submit'` | `POST /submit` |
| `'resume'` | 어느 상태로 되돌릴지 묻는 창 (반려 · 취소 · 완료) |

`primary` 가 `null` 인 상태는 중복 하나뿐이다 — 서버가 상태 변경을 막는다.

`statusMeta.test.js` 가 이미 "모든 상태에 항목이 있는가"를 검사한다. 같은
자리에 `primary` 검사를 더한다 — 상태를 추가하고 여기를 빼먹으면 버튼이
조용히 사라지는 것이 유일한 증상이다.

### 상태별로 무엇이 나오는가

| 상태 | 주 버튼 | 무엇이 일어나나 | `⋯` 메뉴 |
|---|---|---|---|
| 작성중 | 검토 요청 | `POST /submit` | (3차+) 다른 상태로 · 중복 병합 |
| 검토대기 | 검토 시작 | 착수 창 | 개발중 · QA중 · 승인대기 · 작성중으로 · 중복 병합 · 반려 |
| 검토중 | 개발 시작 | `PATCH /status` | QA중 · 승인대기 · 검토대기로 · 중복 병합 · 반려 |
| 개발중 | QA 시작 | `PATCH /status` | 승인대기 · 검토중으로 · 중복 병합 · 반려 |
| QA중 | 승인 요청 | `PATCH /status` | 개발중으로 · 중복 병합 · 반려 |
| 승인대기 | 승인하고 완료 | 승인 창 | QA중으로 · 중복 병합 · 반려 |
| 완료 | 재개 | 상태를 고르는 창 | 중복 병합 |
| 반려 · 취소 | 재개 | 상태를 고르는 창 | 중복 병합 |
| 중복 | — | | 없음 — 서버가 상태 변경을 막는다 |

메뉴에는 `BOARD_STATUSES` 중 지금 상태와 주 버튼의 목적지를 뺀 전부가 들어간다.
**건너뛰기가 흔하기 때문이다** — 실제 전이 26건 중 검토대기에서 나간 길이 여덟
가지였고, 그중 `검토중` 은 33%였다. 다음 걸음만 버튼으로 꺼내고 나머지를 잠그면
안 된다.

`완료` 는 어느 목록에도 넣지 않는다. 서버가 `PATCH /status` 로 오는 완료를
거부한다(`'완료는 승인 절차로만 처리할 수 있습니다.'`). 지금은 고를 수 있어
보였다가 승인 창이 뜨는데, 이건 화면이 서버 규칙과 어긋난 것이다.

### 반려는 안으로, 취소는 밖으로

지금은 둘 다 상태 아래 붉은 알약이라 **파괴적 행동이 화면에서 가장 눈에 띈다.**

**반려**(3차 이상, IT의 결정)는 `⋯` 안으로 넣는다. **취소**(4차도 가능, 요청한
쪽이 거두는 것)는 밖에 남긴다 — 요청자에게는 그것이 이 화면에서 할 수 있는
유일한 행동이라, 메뉴에 숨기면 길이 사라진다.

둘 다 사유가 필수다. 지금 `CloseActions` 가 하는 일을 그대로 옮긴다.

## 4. 오른쪽 열

**여기서 바꾸는 것 넷만 남긴다.** 담당자 · 상태 · 배포예상일 · 레드마인.

그 아래 접힌 `요청 내용` 에 카테고리 · 채널 · 우선순위 · 요청자 · 요청일이
들어간다. 지금 이 자리에 붙어 있는 `요청 내용 · 수정에서 변경` 이라는 문구는
사라진다 — 바꾸는 자리에 없으니 변명할 것이 없다.

**빈 값은 `—` 대신 `＋ 정하기` 로 유도한다.** 배포예상일은 44건 중 7건,
레드마인은 1건만 채워져 있다. 지금 방식이면 네 줄 중 절반이 늘 회색 `—` 라
그 영역이 죽어 보인다.

**색을 갖는 행은 하나다.** 이 화면에서 지금 잘못된 상태 — 대개 담당자 미지정 —
만 노랗다. 나머지가 회색이라야 그 한 줄이 눈에 박힌다.

`유형`은 머리 줄의 뱃지로 옮긴다. 누를 수 있다는 것이 보여야 하므로 점선
테두리를 쓰고, 미분류(2건)일 때는 `유형 정하기` 로 표시한다.

## 5. 본문

카드 세 개(`As-Is` · `To-Be` · `비고`)를 걷어내고 문서 한 장으로 만든다.
섹션 제목만 남기면 읽는 순서가 생긴다.

순서는 지금 그대로 `As-Is → To-Be` 다. 문제를 먼저 읽는 것이 자연스럽고,
뒤집으면 낯설어진다. 대신 **To-Be 에만 왼쪽 강조선**을 준다 — 실무자가 이
화면에서 찾는 것은 "뭘 만들어야 하나"다.

`비고` 는 접는다. 본문 폭은 68ch 로 제한한다. 지금은 1,200px 카드에 텍스트가
꽉 차서 한 줄을 눈으로 따라가기 버겁다.

본문 아래 순서는 **첨부 → 연결 → 하위 작업 → 비고 → 대화** 다.

## 6. 첨부

**비율을 지켜 크게 보여준다.** `object-cover` 를 `object-contain` 으로 바꾸고
높이 제한을 둔다(최대 360px).

근거는 실제 데이터다. 첨부가 있는 건은 44건 중 7건이고 **평균 1.6장, 최대
3장**이다. 자리를 아낄 이유가 없다. 그리고 9개가 PNG — 가로로 긴 화면 캡처를
80px 정사각형에 잘라 넣으면 가운데 한 조각만 남는다.

1장이면 본문 폭 전체, 2~3장이면 가로로 나눈다.

**누르면 같은 페이지에서 확대된다.** 새 탭으로 나가면 To-Be 와 대조할 수 없다.
`Lightbox` 컴포넌트를 새로 만든다 — 이 화면에서 첨부가 판단 근거인 이상 값어치가
있다.

엑셀·PDF 등 미리보기가 안 되는 파일은 지금처럼 아이콘 + 파일명 + 크기 행으로
둔다. 삭제 버튼은 올려놨을 때만 나타나게 한다 — 지금은 썸네일 위에 항상 떠
있어서 보려다 지울 수 있다.

**첨부가 As-Is 것인지 To-Be 것인지는 구분하지 않는다.** 스키마가 소속을 모른다
(`requirement_id` 와 `sort_order` 뿐). 컬럼을 늘려야 하므로 실제로 헷갈리는
것이 확인된 뒤에 한다.

## 7. 대화 · 하위 작업 · 연결

**대화를 본문 바로 아래로 올린다.** 지금은 스크롤 맨 끝이다. 코멘트 42건이
이 앱에서 유일하게 살아 있는 협업 신호인데 화면이 그렇게 대접하지 않고 있다.
`ActivityFeed` 는 그대로 쓴다 — 변경 이력과 코멘트를 시간순으로 합치는 일을
이미 한다.

**하위 작업은 자리만 준다.** `ChecklistSection` 은 이미 구현돼 있고 3차 이상이
항목을 추가·완료 표시한다. 다만 운영 데이터가 **0개**다.

본문의 `[요건 1]~[요건 4]` 를 여기로 옮기면 진척을 셀 수 있다. 하지만 그건
요청 작성 방식을 바꾸는 일이고, 이 재설계의 목적("멈춘 게 멈춰 보이게")과 다른
문제(진척 추적)를 푼다. 한 번에 둘을 하면 어느 쪽이 효과가 있었는지 알 수 없다.
자리를 제대로 주고, 실제로 쓰이기 시작하는지 본다.

**연결(`RequirementLinks`)은 지금 자리 그대로** 본문 열에 둔다. 1건 사용 중이다.

## 8. 모바일

지금 코드는 오른쪽 열 **전체**를 `order-first` 로 본문 위에 올린다. 주석에
이유가 적혀 있다 — *"폰으로 상세를 여는 이유는 '내 요청 어디까지 왔나' 하나"*.

머리 줄이 그 일을 하게 되므로, **머리 줄과 진행 스트립만 상단에 두고 오른쪽
열은 본문 아래로 내린다.** 본문에 닿기까지의 스크롤이 짧아진다.

주 버튼은 가로 전체 · 높이 40px. 지금 승인 버튼이 `h-11` 인 것과 같은 이유다.

`RequirementDetail.jsx` 에는 데이터 로딩과 핸들러, 그리고 조립만 남는다.
목표는 400줄 아래다.

**핸들러는 옮기지 않는다.** `changeStatus` · `closeRequirement` ·
`changeAssignee` 같은 것들은 `RequirementDetail` 에 그대로 두고 props 로
내려보낸다. 상태(`data`)가 거기 있고, 옮기면 각 컴포넌트가 자기 fetch 를 갖게
되어 화면이 부분적으로 낡는다.

## 10. 디자인 시스템 1차 승격

이 화면에서 나온 조각을 토큰과 컴포넌트로 올린다. **먼저 만들고 화면에 쓰는
것이 아니라, 화면에 쓴 것을 뽑아 올린다.**

지금 코드베이스는 생색 유틸리티 996곳 대 shadcn 토큰 97곳이다(9%). 이번에
만드는 파일들은 토큰으로만 쓴다. 나머지 이관은 다음 화면(목록 · 보드 · 회의)에서
같은 언어로 옮기며 한다.

`red` 59회와 `rose` 40회가 같은 '위험'을 두 이름으로 쓰고 있다. 새 파일에서는
`rose` 하나로 통일한다 — 지금 상태 뱃지(`statusMeta`)가 rose 계열이라 그쪽이
기준이다.

## 11. 서버는 바뀌지 않는다

라우트 · 권한 · 알림은 한 줄도 손대지 않는다. 이번 작업은 전부 화면이다.

화면이 지켜야 할 서버 규칙은 다음과 같고, 전부 지금도 서버가 다시 판정한다.

| 규칙 | 어디서 |
|---|---|
| 상태 변경은 3차 이상 | `requireBrandAccess(brandId, '3차')` |
| 완료는 `PATCH /status` 로 불가 | `status/route.js` |
| 병합된 건은 상태 변경 불가 | 같은 곳 |
| 반려는 3차 이상, 취소는 4차부터 | `close/route.js` |
| 반려·취소는 사유 필수 | 같은 곳 |
| 담당자 본인은 승인 불가 | `lib/approval.js` `canApprove` |
| 검토 요청은 본인의 작성중 건만 | `lib/submitRequirement.js` |
| 담당자는 그 브랜드 소속만 | `assignee/route.js` |
| 삭제는 전체 관리자 | `[id]/route.js` DELETE |

## 12. 테스트

순수 함수와 판정에 건다. 렌더 테스트는 이 프로젝트에 선례가 없어 만들지 않는다.

**`lib/statusMeta.test.js` (기존 파일에 추가)**
- 모든 상태에 `primary` 가 있다 (`null` 도 명시적 값으로 친다)
- `primary.to` 는 `REQUIREMENT_STATUSES` 안의 값이거나 `null`
- `중복` 의 `primary` 만 `null` 이다
- `primary.via` 가 `'direct'` 인 상태의 `to` 는 `DIRECT_STATUSES` 안에 있다
  — 화면이 서버가 거부할 상태를 버튼으로 내밀지 않는지가 이 검사의 요점이다

**`lib/statusActions.js` + 테스트 (새 파일)**
`⋯` 메뉴에 무엇이 들어가는지를 정하는 순수 함수를 뺀다.

```js
menuTransitions({ status, tier, isGlobalAdmin }) -> string[]
```

- 지금 상태와 주 버튼 목적지는 빠진다
- `완료` 는 절대 들어가지 않는다
- 중복 상태에서는 빈 배열
- 4차에게는 빈 배열
- 반려는 3차 이상에게만

**`lib/headline.js` + 테스트 (새 파일)**
머리 줄 문구를 정하는 순수 함수.

```js
headline({ requirement, stalledDays, viewer }) -> { tone, text, action }
```

- 정체 14일 이상이면 `tone: 'stall'`
- 완료 건은 경과가 아니라 소요를 말한다
- 요청자에게는 `담당자를 기다리고 있습니다`
- 승인대기 · 담당자 본인이면 `action: null`
- 예상일이 지났으면 지연 알약이 붙는다

## 범위 밖

**요건을 하위 작업으로 옮기기** — 7절 참고. 자리만 주고 지켜본다.

**첨부를 As-Is / To-Be 로 가르기** — 스키마가 소속을 모른다. 컬럼을 늘려야
하므로 실제로 헷갈리는 것이 확인된 뒤에 한다.

**주석(annotation) 기능** — `annotated_image_url` 과 `annotation_data` 가
스키마에 있으나 코드 어디에도 없고 사용 0건이다. 죽은 컬럼이다.

**편집 모드** — `수정` 을 누르면 화면 전체가 폼이 된다. 이번에는 읽는 화면만
손대고 폼은 그대로 둔다. 머리 줄과 진행 스트립은 편집 중에도 남는다.

**목록 · 보드 · 회의 화면** — 여기서 나온 컴포넌트로 다음에 옮긴다.

**생색 996곳 일괄 이관** — 새로 만드는 파일만 토큰을 쓴다. 나머지는 화면을
옮길 때 함께 정리한다.
