# QA·최종 승인 단계 설계

**작성일:** 2026-08-03
**대상:** 모아 MOA (요구사항 관리)
**버전:** v1.4

## 목적

두 가지를 요구사항 흐름에 추가한다.

1. **QA 단계** — 개발이 끝난 뒤 테스트가 진행 중인 구간을 눈에 보이게 한다.
2. **최종 승인 단계** — 요청한 쪽(브랜드) 또는 온라인본부가 "요청한 대로 됐다"를
   확인하고 나서야 완료로 넘어가게 한다.

승인 시 남는 확인 기록은 나중에 요구사항을 정리하고 타 브랜드로 확산할 때
재료가 된다. **정리·확산 화면 자체는 이 스펙의 범위가 아니다** — 아래 "범위 밖"
참조.

## 범위 밖 (다음 사이클)

- 완료된 요구사항을 모아 보는 정리 화면
- 타 브랜드 확산 가능 여부 표시·필터

승인 시점에 "타 브랜드에도 적용 가능한가"를 묻는 안을 검토했으나 뺐다.
브랜드 담당자는 자기 브랜드만 알기 때문에 그 판단을 할 수 없고, 그 칸을 폼에
두면 근거 없이 체크하거나 비워 두게 되어 반쪽짜리 데이터가 남는다. 이 판단은
여러 건을 놓고 비교할 수 있는 본부가, 정리하는 시점에 하는 것이 맞다. 그때는
아래에서 쌓는 `확인 내용` 텍스트가 분류 재료가 되어 있다.

## 상태 흐름

```
작성중 → 검토대기 → 검토중 → 개발중 → QA중 → 승인대기 → 완료
(브랜드)  (IT 차례)   (IT)     (IT)    (IT)  (브랜드·본부)
```

상태 이름은 기존 규칙("지금 누구 차례인지가 드러나게")을 따른다. QA중은
개발팀이 들고 있는 구간이고, 승인대기는 브랜드·본부가 들고 있는 구간이다.
두 구간의 대기 주체가 다르므로 한 칸으로 합치지 않는다.

보드 컬럼은 5개에서 7개가 된다. 이미 가로 스크롤이 있고 종결 상태(반려·취소·
중복)는 컬럼이 아니므로 더 늘지 않는다.

### 전환 규칙

| 전환 | 방법 | 권한 |
|---|---|---|
| `완료`를 제외한 보드 상태 간 이동 | 보드 드래그, 상세 Select (지금과 동일) | 3차 이상 |
| **모든 상태 → `완료`** | 승인 다이얼로그를 거친다 | 아래 승인 권한 |
| 보드 상태 → 반려·취소 | 기존 종결 흐름(`close` 라우트) | 기존과 동일 |

**뒤로 가는 전환은 새로 만들지 않는다.** QA에서 문제가 나오면 `개발중`으로
드래그하거나 상세 Select 에서 고르면 된다 — 지금도 보드 상태끼리는 자유롭게
오간다. 되돌아간 사실은 상태 이력에 남고 이유는 코멘트에 적는다. "QA 반려"
라는 별도 기능을 만들면 같은 일을 하는 두 번째 길이 생길 뿐이다.

### `완료`로 가는 모든 길이 승인을 지난다

출발지를 가리지 않는다. `개발중 → 완료`처럼 QA와 승인대기를 건너뛰는 것도
막지 않지만, 그 경우에도 승인 다이얼로그를 지나야 한다.

승인대기에서 올 때만 다이얼로그를 띄우면 `개발중 → 완료`가 우회로가 되어
이번에 만드는 것 전체가 선택사항이 된다. 반대로 "완료는 승인으로만 도달한다"로
하면 절차를 건너뛰더라도 누가 확인했다는 기록은 반드시 남는다.

절차 자체를 강제하지 않는 이유: 급한 건이나 문서 수정 같은 사소한 건까지
QA중을 거치게 하면 사람들은 규칙을 우회할 방법부터 찾는다. 통과시키되 흔적을
남기는 편이 낫다. 건너뛴 사실은 상태 이력(`개발중 → 완료`)에 그대로 보인다.

## 승인

### 성립 조건

**한 명이 승인하면 성립한다.** 브랜드와 본부 양쪽 승인을 모두 요구하지 않고,
순서도 강제하지 않는다. 필요한 것은 "누가 되었든 최종 확인이 되었다"는 기록이다.

### 승인 권한

- **그 요구사항을 볼 수 있는 사람이면 누구나** (`requireBrandAccess(brandId, '4차')`)
- 전체 관리자는 언제나 가능
- **단, 담당자(assignee) 본인은 제외**

"브랜드 사람 또는 본부 사람"이라고 쓰지 않는다. `team_members.affiliation`
(브랜드/본부)은 가입 시 자기 신고값이라 어떤 권한 판단에도 쓰지 않기로 되어
있다(`app/api/signup/route.js` 주석). 본부 사람도 실제로는 `user_brand_roles`
배치나 `is_global_admin` 을 통해 그 브랜드 건에 접근한다. 그러므로 승인 권한은
"접근 권한이 있는가" 하나로 충분하고, 그것이 곧 브랜드·본부 양쪽을 포괄한다.

담당자 제외가 유일한 제약이다. 이것이 없으면 개발 → QA → 본인 승인이 되어
도장 찍기가 되고, 점검 단계를 만드는 목적과 정면으로 충돌한다. 제약이 이 하나
뿐이라 나머지 흐름은 막히지 않는다.

담당자 본인이 완료로 옮기려 하면 **다이얼로그를 띄우지 않고** 바로 안내한다:

> 담당자 본인은 승인할 수 없습니다. 브랜드 또는 본부의 다른 분께 확인을 요청해 주세요.

폼을 띄워 적게 한 다음 거절하는 것은 시간 낭비다.

### 승인 시 받는 것

**확인 내용(필수)** 하나. 반려·취소가 사유를 필수로 받는 것과 같은 무게다.

무엇을 확인했는지가 안 남으면 점검 단계를 만드는 의미가 없다. 마찰이 있는
것은 이 단계의 성질이지 결함이 아니다.

점검 항목 자체를 위한 별도 체크표는 만들지 않는다. **하위 작업 체크리스트
(v1.3, `requirement_checklist_items`)**에 "데이터 파이프라인 설계 확인" 같은
항목을 적으면 된다. 이미 있는 것을 쓴다.

### 기록

`change_logs` 에 한 줄:

```
change_type = '상태변경'
field_name  = 'status'
old_value   = <직전 상태>
new_value   = '완료'
comment     = <확인 내용>
changed_by  = <승인자>
```

새 테이블을 만들지 않는다. 승인은 상태 변경의 한 종류이고, `change_logs` 는
이미 누가·언제·무엇을 바꿨는지를 담고 있다. 별도 테이블을 두면 상태 구간 계산
(`lib/statusDurations.js`)이 두 곳을 봐야 한다.

`completed_at` 은 기존 `computeCompletedAt` 규칙대로 채워진다.

## 구현

### 마이그레이션 0017

`requirements_status_check` 제약에 `QA중`, `승인대기` 추가. 데이터 변환 없음 —
기존 요구사항은 전부 지금 상태 그대로다.

```sql
alter table requirements drop constraint if exists requirements_status_check;
alter table requirements add constraint requirements_status_check
  check (status in ('작성중','검토대기','검토중','개발중','QA중','승인대기',
                    '완료','반려','취소','중복'));
```

위 목록은 `0009_requirement_fields.sql` 의 현재 제약
(`'작성중','검토대기','검토중','개발중','완료','반려','취소','중복'`)에
`QA중`·`승인대기` 둘만 더한 것이다. 확인 완료 — 0009 이후 상태를 건드린
마이그레이션은 없다.

### 새로 만드는 것

**`lib/statuses.js` (수정)**

```js
export const QA_STATUS = 'QA중';
export const APPROVAL_PENDING_STATUS = '승인대기';

export const REQUIREMENT_STATUSES = [
  '작성중', '검토대기', '검토중', '개발중', 'QA중', '승인대기',
  '완료', '반려', '취소', '중복',
];

export const BOARD_STATUSES = [
  '작성중', '검토대기', '검토중', '개발중', 'QA중', '승인대기', '완료',
];

// 드래그·Select 로 바로 갈 수 있는 상태. 완료는 승인 라우트로만 도달한다.
export const DIRECT_STATUSES = BOARD_STATUSES.filter((s) => s !== DONE_STATUS);
```

`BOARD_STATUSES` 는 컬럼 목록이므로 완료를 포함한 채로 둔다. 완료 컬럼은
보드에 있어야 한다.

**`lib/approval.js` (신규, 순수 함수 + 테스트)**

`lib/submitRequirement.js` 와 같은 모양이다.

```js
// { allowed: boolean, reason: string|null }
export function canApprove({ requirement, actor })
```

판정 순서와 각 거절 사유:
1. 이미 `완료`이면 거절 — `'이미 완료된 요구사항입니다.'`
2. 종결 상태(반려·취소·중복)이면 거절 — `'종결된 요구사항은 승인할 수 없습니다.'`
3. `actor.isGlobalAdmin` 이면 허용
4. `requirement.assignee === actor.memberId` 이면 거절 —
   `'담당자 본인은 승인할 수 없습니다.'`
   (`submitRequirement.js` 와 같이 `Boolean(requirement.assignee)` 가드를 둔다.
   둘 다 `undefined` 일 때 통과해 버리는 사고를 막는다.)
5. 그 외 허용

브랜드 접근 여부는 여기서 보지 않는다 — 라우트의 `requireBrandAccess(brandId,
'4차')` 가 이미 판정하므로 두 곳에서 같은 규칙을 두 벌로 갖지 않는다.

**`POST /api/requirements/[id]/approve` (신규)**

- 입력: `{ brandId, reason }`
- `reason` 이 비면 400 — `'확인 내용을 입력해 주세요.'`
- `requireBrandAccess(brandId, '4차')`
- 대상 조회 → `canApprove` 판정 → 거절이면 403 + 사유
- `status = '완료'`, `completed_at = computeCompletedAt(...)`, `updated_at` 갱신
- `change_logs` 한 줄 기록
- `notifyStatusChange` 호출 (실패해도 조용히 넘어감 — 기존 규약)

**`PATCH .../status` (수정)**

받는 목록을 `BOARD_STATUSES` 에서 `DIRECT_STATUSES` 로 바꾼다. 완료를 보내면
400 — `'완료는 승인 절차로만 처리할 수 있습니다.'`

서버가 관문이므로 화면 코드를 우회해도 막힌다.

**`components/ApprovalDialog.jsx` (신규)**

보드와 상세가 **같은 컴포넌트를 쓴다.** 두 벌로 만들면 한쪽만 고치는 날이 온다.

- props: `open`, `onOpenChange`, `requirement`, `brandId`, `onApproved`
- 확인 내용 입력(필수, 최대 500자) + 승인/취소 버튼
- 건너뛴 경우 안내: 출발 상태가 `승인대기` 가 아니면
  *"QA중·승인대기를 거치지 않았습니다. 이력에 그대로 남습니다."* 를 보여준다.
  막지는 않는다.

### 손대야 하는 곳

상태가 늘어나면 조용히 틀리는 자리들이다.

| 파일 | 할 일 |

`StatusGuide` 가 빠지면 팀에 설명할 근거가 없다. 필수 항목이다.

### 낙관적 갱신을 하지 않는 유일한 전환

`완료`로 갈 때만 카드를 먼저 옮기지 않는다. 옮겨놓고 다이얼로그를 닫으면
되돌리는 순간이 깜빡여서 승인이 된 건지 만 건지 헷갈린다. 이 전환은
**성공한 뒤에 움직인다.**

나머지 전환은 지금 그대로 낙관적으로 옮기고 실패 시 롤백한다.

## 자동으로 맞는 것 (손대지 않음)

확인한 결과 다음은 코드 변경 없이 동작한다.

- **상태 필터** — `REQUIREMENT_STATUSES` 를 그대로 쓰므로 두 개가 늘어난다
- **지연 판정(`isOverdue`)** — QA중·승인대기는 `CLOSED_STATUSES` 가 아니므로
  지연 대상에 포함된다
- **상태 구간(`lib/statusDurations.js`)** — `field_name === 'status'` 로 거르므로
  새 상태의 구간이 자동으로 잡힌다. `QA중 3일`, `승인대기 5일` 이 보인다.
  **어디서 막히는지가 여기서 드러난다**
- **대시보드** — 미완료 집계에 자연히 들어간다

## 기존 데이터

이미 `완료`인 요구사항은 건드리지 않는다. 승인 기록 없이 완료된 건들이 그대로
남는다 — 소급해서 누가 확인했다고 적을 수는 없다.

## 테스트

- `lib/approval.test.js` — `canApprove` 의 5개 판정 경로 각각, 그리고
  `assignee`/`memberId` 가 둘 다 `undefined` 인 경우 거절되지 않는지
- `lib/statuses` 관련 기존 테스트에 `DIRECT_STATUSES` 가 완료를 포함하지 않는지

라우트와 화면은 기존 관행대로 자동 테스트를 두지 않고 브라우저에서 확인한다.
