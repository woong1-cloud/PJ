## 왜 지금인가

1단계를 만들 때 기준으로 삼은 파일은 `신규브랜드_온라인오픈_체크리스트_v10.xlsx` 였다.
그 뒤로 파일이 v20 까지 갔고, 통합 WBS 로 모양이 다시 잡혔다.

**지금 가져오기로는 이 파일에서 한 건도 안 들어온다.** 그것 하나만으로도 2단계의
첫 덩어리가 정해진다.

그리고 사용자가 한 말이 이 스펙의 축이다.

> 상세내용은 사실 확정적이지 않아. 언제든지 추가되거나 삭제되어야 하는 내용들이 있어.

1단계는 "403건을 한 번 넣고 쓴다"를 전제로 만들었다. 그 전제가 틀렸다.
목록은 매주 흔들린다. 흔들리는 것을 다루는 것이 2단계다.

## 1. 이 파일이 말해준 것

### 구조가 두 층이 됐다

| 시트 | 무엇 | 건수 |
|---|---|---|
| `00_개요` | 제반사항 · **먼저 결정할 것** · 시트 구성 · 역할 요약 | 134행 |
| `01_WBS` | 과업 — ID·구분·핵심 과업·**쉬운 설명**·주관·참여·시작·종료·상세 시트 | 90 |
| `02_간트` | 과업 × 주차 26 막대 | 90 |
| `D01`~`D19` | 세부 체크 항목 — v10 과 같은 열 **+ `진행상태`** | 476 |

### 두 층은 지금 만들지 않는다

데이터가 못 받친다.

- 상세 476행 중 **W ID 를 가진 행이 0건**. 연결은 `상세 시트` 열(시트 단위)뿐이다
- `01_WBS` 의 `항목` 합계가 **408 ≠ 476**

두 층을 만들면 476건의 소속을 사람이 손으로 채워야 하는데, 그것이 바로 "확정적이지
않은" 부분이다. 세부만 가져간다. 과업 층은 **4단계 타임라인에서 다시 본다** — 간트가
이미 과업 90 × 주 26 으로 그려져 있어서 그때 값을 한다.

`01_WBS` 의 `쉬운 설명` 90줄은 이 파일에서 가장 좋은 자산인데 지금은 붙일 자리가
없다. 버리는 것이 아니라 미루는 것이다.

### 이 팀은 지우지 않고 '제외'한다

476건 중 **25건**이 `상태 = 해당없음` · `진행상태 = 제외` 다. 비고에 이유가 남아 있다.

> `[중복] 01-22에서 관리 — 이 시트에서는 제외`

지웠으면 이 문장이 없다. 그리고 다음 사람이 같은 항목을 다시 넣는다.
**삭제가 아니라 제외**가 이 팀의 실제 습관이고, 그것을 그대로 받는다.

### 코드가 `07B-01` 을 쓴다

| 앞자리 | 건수 | 시트 |
|---|---|---|
| `07B` | 26 | D08_WMS·재고 |
| `10A` | 13 | D11_자사몰연결 |
| `10B` | 12 | D12_외부몰연결 |

`parseRow` 가 `/^\d{2}-\d{2}$/` 로 검사하므로 **51건이 조용히 버려진다.**
`parseDeps` 도 같은 정규식이라 이 51건을 가리키는 선행조건도 함께 사라진다.

### 역할 사전이 없다

`24_R&R분배` 가 사라졌다. `parseRoles` 는 0종을 돌려준다 — 이미 그렇게 동작하므로
깨지지는 않는다.

대신 역할이 항목 안에 있다: **주관 16종 · 지원 16종**. 역할 목록이 필요하면
항목에서 `distinct` 로 뽑는다. 사전을 따로 만들지 않는다 — 두 벌이 되면 갈린다.

## 2. 가져오기를 다시 만든다

### 2.1 시트를 이름으로 고르지 않는다

지금은 `/^(0[1-9]|1[0-8])_/` 다. 이 규칙이 이번에 두 번 틀렸다.

- `01_WBS` · `02_간트` 를 항목 시트로 **오인**한다
- `D01`~`D19` 를 **건너뛴다**

`D` 를 정규식에 더하는 것은 같은 실수를 한 번 더 하는 것이다. 다음 파일은 또 다른
이름을 쓴다.

**머리 행으로 고른다.** `ID` · `체크 항목` · `D-day` 세 열을 모두 가진 행이 있는
시트가 항목 시트다. `findHeaderRow` 가 이미 그 일을 한다 — 판정을 이름에서 머리로
옮기기만 하면 된다.

```js
// 바뀜: 이름이 아니라 머리 행이 정한다
export function isTaskSheet({ name, rows }) {
  return findHeaderRow(rows, REQUIRED) >= 0;
}
```

`01_WBS` 는 `체크 항목` · `D-day` 가 없어서 자동으로 빠진다. `02_간트` 도 같다.
`00_개요` 도 같다. 이름 목록을 유지하지 않아도 된다.

**부르는 쪽이 바뀐다.** `isTaskSheet(name)` → `isTaskSheet({ name, rows })`.
`parseSheet` · `parseWorkbook` 과 기존 테스트가 함께 바뀐다. `name` 은 워크스트림
이름으로 여전히 쓰이므로 인자에서 빼지 않는다.

**되짚을 위험:** 파생 시트가 우연히 세 열을 다 갖는 경우. v10 의 `23_주간회의`가
그럴 수 있다. 그때는 같은 코드가 두 번 들어오는데, `parseWorkbook` 이 이미
코드로 합치므로 중복은 안 생긴다. 다만 뒤엣것이 이기므로 파생이 원본을 덮을 수
있다 — 미리보기에 시트 이름과 건수를 그대로 보여 사람이 알아채게 한다.

### 2.2 코드 형식

```js
const CODE = /^\d{2}[A-Z]?-\d{2}$/;   // 01-01, 07B-01, 10A-03
```

`parseRow` 와 `parseDeps` 둘 다 고친다. 한쪽만 고치면 항목은 들어오는데 선행조건이
안 이어진다.

### 2.3 제외를 읽는다

|시트 값|모아|
|---|---|
|`상태 = 해당없음`|`해당없음`|
|`진행상태 = 제외`|`해당없음`|
|그 밖|`할 것`|

**`상태` 열의 나머지 값(미착수·진행중…)은 여전히 안 읽는다.** 1단계에서 정한
그대로다 — 시트의 진행 상태와 모아의 상태가 갈리면 어느 쪽이 맞는지 아무도 모른다.

`해당없음`만 예외인 이유: 그것은 진행 상태가 아니라 **범위**다. "이 브랜드에는
해당 없다"는 판단이고, 가져올 때 한 번 반영하면 끝난다.

### 2.4 런칭에 직접 가져온다

**이것이 1단계 설계의 오류를 고치는 부분이다.**

지금 길은 하나다: `엑셀 → 가이드 → 복제 → 런칭`. 항목은 값 복사라 가이드를 고쳐도
진행 중인 런칭에 안 닿는다. 그 원칙 자체는 맞다 — 진행 중에 몰래 바뀌면 화면을 못
믿는다. 문제는 **길이 하나뿐**이라는 것이다.

이 파일은 가이드(브랜드 무관 지식)가 아니라 **HOKA 런칭 그 자체**다. 오픈일이
박혀 있고, 신규 법인이고, 채널이 정해져 있다. 그리고 계속 바뀐다.

그래서 길을 하나 더 낸다.

```
엑셀 → 가이드  → 복제 → 런칭      (다음 브랜드를 위한 지식)
엑셀 → 런칭                        (지금 이 브랜드, 매주 갱신)   ← 새로
```

가이드는 그대로 둔다. 런칭이 끝난 뒤 되먹임(4단계)으로 자란다.

### 2.5 재가져오기 규칙

**같은 파일을 열 번 올려도 안전해야 한다.** 그러지 않으면 아무도 두 번 안 올린다.

| 상황 | 무엇을 한다 | 왜 |
|---|---|---|
| 새 코드 | 항목을 만든다 (`할 것`) | |
| 있는 코드 | **계획 열만 갱신** | 제목·D-day·역할·선행·산출물·비고·채널·대분류 |
| 있는 코드 | **진행은 안 건드린다** | 상태·담당·막힌 이유·완료 시각. 이걸 지우면 재가져오기가 회의 결과를 지운다 |
| 시트에서 사라짐 | **`해당없음` 으로 바꾸고 표시를 남긴다** | 사용자 결정 |
| 사라졌는데 이미 `완료` | 그대로 둔다 | 이미 한 일이다. 없던 일로 만들 수 없다 |
| 사라졌는데 이미 `해당없음` | 그대로 둔다 | |
| 사라졌는데 손으로 넣은 항목 | 그대로 둔다 | 시트 밖에서 난 일이라 시트에 없는 게 당연하다 |
| 다시 나타남 (가져오기가 뺐던 것) | `할 것` 으로 되살린다 | |
| 다시 나타남 (사람이 뺐던 것) | **그대로 둔다** | 사람의 판단이 파일보다 세다 |

마지막 두 줄을 가르기 위해 `excluded_by` 를 둔다 (`import` | `user`).
이게 없으면 사람이 "우리 브랜드엔 해당 없음"으로 뺀 항목이 다음 가져오기마다
되살아난다.

미리보기에 그대로 보여준다.

```
새로 23건 · 갱신 451건 · 해당없음으로 2건
  02-14  상표권 국문 출원 (시트에서 사라짐)
  13-27  인플루언서 시딩 (시트에서 사라짐)
손대지 않음 4건 — 완료 2 · 사람이 제외 1 · 손으로 넣은 것 1
```

## 3. 해당없음

`launch_tasks.status` 에 다섯째 값을 더한다.

```
'할 것' | '하는 중' | '완료' | '막힘' | '해당없음'
```

별도 boolean 을 두지 않는 이유: 시트가 이미 `상태` 열에 `해당없음` 을 쓰고 있다.
같은 말을 두 축으로 나누면 "완료면서 해당없음"이 만들어지고, 그때 진척률이 무슨
뜻인지 아무도 모른다.

### 진척률에서 뺀다

```js
// lib/launchTask.js
export function progress({ tasks = [], openDate, today } = {}) {
  const list = (tasks ?? []).filter((t) => !isNotApplicable(t));
  ...
}
```

**분모에서 빠지는 것이 요점이다.** 476건 중 25건이 해당없음이면 분모는 451이다.
안 빼면 아무리 해도 95%가 천장이 되고, 그 순간 진척률이 아무 말도 안 하게 된다.

`isLate` · `isThisWeek` · `isWaitingOnDep` 도 해당없음을 뺀다 — `isDone` 을 빼는
것과 같은 이유다. 안 한 일이 아니라 **할 일이 아닌** 것이다.

### 화면

상태 단추는 넷 그대로다. 해당없음은 행 끝 `⋯` 메뉴에 둔다.

자주 누르는 것이 아니고, 다섯째 단추를 476줄에 붙이면 줄이 넘친다. 되돌리는 것도
같은 메뉴에서 한다.

해당없음인 줄은 흐리게, 취소선 없이. 완료와 달라 보여야 한다 — 하나는 끝난 것이고
하나는 애초에 안 하는 것이다.

## 4. 런칭 항목을 손으로 더하고 뺀다

지금 항목 추가·삭제는 **가이드에만** 있다. 런칭에는 없다. 매주 흔들리는 목록에서
이건 뒤집힌 구조다.

- `POST /api/launch/[id]/tasks` — 손으로 하나 더하기. 코드는 서버가 짓는다
  (`lib/launchCode.js` 의 `nextCode`, 워크스트림 안에서)
- `DELETE /api/launch/[id]/tasks/[taskId]` — 지우기

**지우기와 해당없음은 다른 일이다.**

- **해당없음** — 이 브랜드에는 안 하는 일. 이유가 남고, 되돌릴 수 있고, 다음
  브랜드를 위한 기록이 된다. **기본은 이쪽이다.**
- **지우기** — 잘못 넣은 것. 흔적을 남길 가치가 없는 것.

화면에서도 그렇게 보여준다. `⋯` 메뉴에 `해당없음` 이 먼저 오고, `지우기` 는 아래
구분선 밑에 둔다.

손으로 넣은 항목은 `source = 'manual'` 로 표시한다. 재가져오기가 안 건드리는
근거가 이 값이다.

## 5. 결정 대기

### 왜 이것이 2단계인가

`00_개요` 에 이런 표가 있다.

| 시기 | 결정 항목 | 미결 시 영향 | 결정 주체 |
|---|---|---|---|
| 9월 중 | 1차 구축 범위 확정 — 웹앱·앱 기능 경계 | 개발 견적·일정 산정 불가 | 브랜드PM · 개발총괄 |
| 10월 초 | 앱 출시 시점 — 오픈 동시 vs 오픈 후 2차 | 오픈 전 3주 부하와 스토어 심사 리스크 | 브랜드 |
| 11월 중 | 오픈 방식 — 동시 오픈 vs 단계 오픈 | 오픈 직전 검수·테스트 부하가 결정됨 | 브랜드 |

**14건이다.** 476건 중 회의에서 실제로 다투는 것은 이것이고, 나머지는 그 결과다.

`미결 시 영향` 이 3단계 협조요청 메일에 담기로 한 바로 그 문장이다 — 왜 지금
답해야 하는지를 그 한 줄이 말한다. 이미 사람이 써 두었다.

그리고 이 화면은 **사람 매핑이 필요 없다.** 결정 주체가 조직 이름으로 적혀 있어서
`launch_members` 없이도 읽힌다. 2단계에 넣을 수 있는 이유가 이것이다.

### 모양

```sql
create table launch_decisions (
  id uuid primary key default gen_random_uuid(),
  launch_id uuid not null references launches(id) on delete cascade,
  seq integer not null,              -- 시트 순서. 사람이 정한 순서를 지킨다
  when_text text,                    -- '9월 중'. 날짜로 바꾸지 않는다
  title text not null,
  impact text,                       -- 미결 시 영향
  owner_text text,                   -- '브랜드PM · 개발총괄'
  status text not null default '대기'
    check (status in ('대기', '결정', '보류')),
  decided_at timestamptz,
  decided_note text,                 -- 무엇으로 정했는지 한 줄
  note text,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (launch_id, seq)
);
```

**`when_text` 를 날짜로 바꾸지 않는다.** 시트가 '9월 중' · '10월 초' 라고 쓴 것은
그 정도로만 정해져 있다는 뜻이다. `2026-09-15` 로 바꾸면 없는 정확도를 만들고,
그 날짜가 지나면 화면이 붉어진다. 있지도 않은 약속을 어겼다고.

정렬은 `seq` 로 한다. 시트가 시기 순으로 적어 두었으니 그 순서를 그대로 쓴다.

### 결정하면

`무엇으로 정했나` 한 줄과 날짜. 이것이 나중에 회의록이 된다.

요구사항의 `ApprovalDialog` 와 같은 생각이다 — "확인했다"가 아니라 "무엇을
확인했는지"를 남긴다.

### 가져오기

`00_개요` 에서 `[먼저 결정할 것]` 블록을 읽는다.

- 시작: `[먼저 결정할 것]` 이 든 행의 **다음** 머리 행 (`시기` · `결정 항목` 포함)
- 끝: 다음 `[` 로 시작하는 행, 또는 시트 끝

`sheetHeader.js` 의 `findHeaderRow` 를 그대로 쓴다. 블록 경계만 새로 만든다
(`lib/launchDecisions.js`).

시트에 이 블록이 없으면 0건이다. 그때는 손으로 넣을 수 있어야 한다 — 다음 브랜드의
파일에 이 표가 없을 수 있다.

**재가져오기 규칙은 항목과 같다.** `seq` 로 맞추고, 결정된 것(`status != '대기'`)은
안 건드린다.

## 6. 주간 진척

런칭 상세의 새 보기. 회의에서 위에서 아래로 읽는 순서 그대로 놓는다.

```
1. 결정 대기         ← 대기 중인 것만
2. 막힘              ← 이유와 함께
3. 기한 지남
4. 이번 주 마감
5. 이번 주 완료      ← done_at 이 최근 7일
```

**결정 대기가 맨 위인 것이 이 순서의 요점이다.** 막힌 것의 원인이 대부분 미결이다 —
개요의 `미결 시 영향` 열이 그것을 그대로 말하고 있다. 결정을 먼저 훑고 막힘으로
내려가면 "이건 아까 그거네"가 된다.

보드의 필터 칩과 겹쳐 보이지만 다르다. 칩은 **하나를 골라 보는** 것이고, 주간 진척은
**다섯을 순서대로 다 보는** 것이다. 회의에서 칩을 다섯 번 누르게 하면 순서가
매번 달라진다.

'이번 주 완료'는 칭찬 자리가 아니라 확인 자리다. 완료로 옮겼는데 실제로는 안 끝난
것이 여기서 걸린다.

기존 `progress()` 를 그대로 쓴다. 새 판정은 **'이번 주 완료'** 하나뿐이다.

```js
// lib/launchTask.js
export function isDoneThisWeek({ task, today } = {}) { ... }   // done_at 이 최근 7일
```

## 10. 범위 밖

**과업 90건(`01_WBS`) 층** — 데이터가 연결을 못 받친다(1절). 4단계 타임라인에서 다시.
