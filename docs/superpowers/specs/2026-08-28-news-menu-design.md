# 소식 메뉴와 의견 보내기 설계

2026-08-28

소식을 도움말 안에서 헤더로 꺼내고, 그 자리에 의견 창구를 함께 연다.

이 문서는 `2026-08-28-feedback-loop-design.md` 의 1절(의견 입구)과 5절(소식)을
고쳐 쓴다. 나머지 절(데이터·메일·관리 화면·승격)은 그대로다.

---

## 왜 지금인가

### 소식이 네 뎁스 안에 있다

지금 소식을 보려면 **계정 메뉴 → 도움말 → 스크롤 → 업데이트 소식** 이다.
팝업(`NewsDialog`)이 한 번 뜨고, 그것을 닫으면 그 뒤로는 아무도 그 네 뎁스를
지나가지 않는다.

배포는 3주 동안 다섯 번 나갔다. 소식은 그 다섯 번을 알리려고 만든 것인데,
전달 경로가 한 번뿐이면 그 한 번을 놓친 사람에게는 없는 기능과 같다.

### 그 한 번마저 X 한 번에 사라진다

지금 `NewsDialog` 는 **X·Esc·바깥 클릭과 "확인했습니다" 를 구분하지 않는다.**
둘 다 `news_seen_at` 을 찍는다. 만들 때의 판단은 "닫고 싶은 사람이 매번 같은
창을 만나면 안 된다" 였고 그 판단 자체는 지금도 맞다.

문제는 그것이 **읽었다는 뜻으로도 쓰인다는 것**이다. 반사적으로 X 를 누른
사람은 팝업도 사라지고 안 읽음 표시도 함께 사라져서, 무엇이 바뀌었는지 알
길이 통째로 없어진다.

### 의견 창구도 같은 곳에 묻힐 참이다

기존 스펙은 `의견 보내기` 를 계정 메뉴의 `도움말` 아래에 두기로 했다. 소식이
거기서 안 읽힌다는 것을 방금 확인했는데, 같은 서랍에 하나를 더 넣는 셈이다.

## 결정 요약

| 무엇 | 결정 |
|---|---|
| 입구 | 헤더에 아이콘 하나. 벨 왼쪽 |
| 담을 것 | 소식 + 의견 보내기 (한 팝오버) |
| 안 읽음 표시 | 점 하나. **"확인했습니다" 와 팝오버 열기에만 사라진다** |
| 팝업 억제 | X 로 닫으면 팝업만 멈추고 점은 남는다 |
| 이름 | `업데이트 소식` 유지 |
| 벨에 통합 | **안 한다** (아래) |
| 전용 페이지 | **안 만든다.** 전체 보기는 `/help#news` |

## 1. 벨에 넣지 않는 이유

인앱 알림은 110건 중 105건이 안 읽혔다. 이미 아무도 안 여는 통이다.

소식을 거기 섞으면 두 가지가 한꺼번에 나빠진다. 소식은 알림 더미에 묻히고,
벨의 숫자는 "읽어야 할 것"과 "한 번 보면 되는 것"이 섞여 더 무의미해진다.

**벨은 나에게 온 것, 새 아이콘은 모아에 생긴 것.** 성격이 다르므로 자리도
따로다.

---

## 2. 헤더 아이콘

### 생김새

```
✨•  🔔  한지웅  (한)
```

`Sparkles` (lucide-react). 관례적으로 "새 기능"을 뜻한다. 확성기는 공지라
더 무겁고, `?` 는 도움말과 겹친다.

벨 왼쪽이다. 오른쪽으로 갈수록 "나" 쪽이다 — 아바타(나), 이름(나), 벨(나에게
온 것), 소식(앱에 생긴 것) 순으로 멀어진다.

모바일에서도 그대로 보인다. 이름이 감춰지는 폭이라 28px 하나 늘어날 자리는
있다.

### 점

안 본 소식이 있으면 인디고 점이 붙는다. 벨의 숫자 배지와 다르게 **숫자가
아니라 점**이다 — 소식은 "몇 건"이 중요하지 않고 "있다/없다"만 중요하다.

### 팝오버

```
┌──────────────────────────────┐
│ 새로 바뀐 것                  │
│                              │
│ 8/30                         │
│ '보류' 상태가 생겼습니다       │
│ 지금은 못 하지만 안 하기로…    │
│                              │
│ 8/29                         │
│ 요청일로 목록을 좁힐 수…       │
│ ─────────────────────────── │
│ 전체 보기      의견 보내기 →  │
└──────────────────────────────┘
```

최근 **3건**까지. 그 이상은 `전체 보기` → `/help#news` 다. 세 건을 넘겨
받으면 팝오버가 화면 절반을 먹고, 오래된 소식은 어차피 안 읽는다.

제목만 늘어놓지 않고 본문까지 담는다. 제목만 보여주면 무엇이 바뀌었는지 알려면
한 번 더 눌러야 하는데, 그러면 뎁스를 줄이려고 만든 것이 다시 뎁스를 만든다.

### 여는 것이 곧 읽는 것이다

팝오버를 열면 `news_seen_at` 을 찍고 점이 사라진다. 여는 행동 자체가 읽는
것이므로 따로 "확인" 을 받지 않는다.

---

## 3. 점을 언제 없애나

**이 설계의 핵심이다.** 아이콘만 늘리면 장식이고, 사람을 부르는 것은 점이다.

| 사용자가 한 일 | 팝업 | 점 |
|---|---|---|
| 팝업의 **확인했습니다** | 다시 안 뜸 | 사라짐 |
| 팝업의 **X · Esc · 바깥** | 다시 안 뜸 | **남음** |
| **헤더 팝오버를 엶** | 다시 안 뜸 | 사라짐 |

X 로 닫은 사람은 팝업에 다시 시달리지 않으면서, 헤더의 점이 계속 그를 부른다.
그가 궁금해지는 순간에 갈 곳이 한 번의 클릭 거리에 있다.

### 서버 컬럼을 안 늘린다

`news_seen_at` 하나 그대로다. **팝업 억제만 브라우저에 저장한다.**

```
localStorage['moa.news.dismissed'] = '2026-08-30'   // 그때의 가장 새 소식 날짜
```

`NewsDialog` 는 안 본 소식이 있고 **그 최신 날짜가 저장된 값보다 클 때만** 뜬다.
날짜를 저장하는 것이 요점이다 — 불린으로 두면 한 번 X 한 사람에게 다음 배포의
팝업도 영영 안 뜬다.

읽을 수 없으면(사생활 보호 모드 등) 안 닫힌 것으로 본다. 팝업을 한 번 더 보는
쪽이 영영 못 보는 쪽보다 가볍다.

---

## 4. 컴포넌트 하나가 둘을 다 안다

`NewsMenu` 를 만들고 `TopBar` 에 붙인다. 이 컴포넌트가

- `/api/me` 를 한 번 불러 `newsSeenAt` 을 읽고
- 아이콘·점·팝오버를 그리고
- 자동으로 뜨는 `NewsDialog` 까지 렌더한다

`app/requirements/layout.js` 의 `<NewsDialog />` 는 걷어낸다.

**한 컴포넌트가 소유하는 이유:** 아이콘과 팝업이 같은 상태(`newsSeenAt`)를
본다. 둘로 나누면 `/api/me` 를 두 번 부르고, 팝업에서 확인을 눌러도 아이콘의
점이 그대로 남는다 — 각자 자기 상태를 들고 있기 때문이다.

`TopBar` 는 요구사항·주간회의·프로젝트·관리·도움말 전부가 쓴다. 팝업이 이제
`/requirements` 밖에서도 뜬다. 로그인 직후 도착하는 곳은 여전히 `/requirements`
라 실제로 달라지는 경우는 드물고, 달라진다면 그것이 맞다 — 소식은 어느 화면에
있든 전할 값어치가 있다.

---

## 5. 의견 보내기

기존 스펙의 1절을 이렇게 고친다.

### 어디에

**소식 팝오버 하단**이 주 입구다. 계정 메뉴에도 `의견 보내기` 를 남긴다 —
한 줄이고, 메뉴에서 찾는 사람이 실제로 있다. 둘 다 같은 창을 연다.

팝오버 하단인 이유: **무엇이 바뀌었나를 읽은 직후가 이건 이렇게 해줬으면을
말하기 가장 좋은 순간이다.** 소식을 읽고 나면 "이것도 되나?" 가 자연스럽게
따라오는데, 지금은 그 생각을 받을 곳이 없다.

### 무엇을 받는가

기존 스펙 그대로 **한 칸**이다.

```
모아를 쓰면서 불편한 점이나 바라는 것을 적어 주세요.
짧아도 괜찮습니다. 읽고 반영되면 알려드립니다.

[                                    ]

                              [보내기]
```

종류·우선순위·화면 경로를 묻지 않는다. 분류는 쓰는 사람보다 읽는 쪽이 잘한다.

### 데이터 · 메일 · 관리 화면 · 승격

기존 스펙 2~4절 그대로다. `moa_feedback` 테이블, 전체 관리자 메일,
`/admin/feedback`, 요구사항 승격.

## 테스트

렌더 테스트는 없다. 테스트 환경이 `node` 라 DOM 이 없다. 판정을 순수 함수로
빼서 그것을 검사한다.

**`lib/newsDismiss.js` (새 파일)**
- 저장된 날짜가 없으면 팝업을 띄운다
- 저장된 날짜가 최신 소식보다 앞서면 띄운다 (새 배포)
- 저장된 날짜가 최신 소식과 같으면 안 띄운다
- 읽을 수 없는 값은 안 닫힌 것으로 본다
- 안 본 소식이 아예 없으면 저장값과 무관하게 안 띄운다

**`lib/newsItems.test.js` (기존에 추가)**
- 팝오버가 자르는 개수(3)만큼은 목록에 늘 있다 — 없으면 빈 팝오버가 뜬다

**`lib/feedback.js` (새 파일)**
- 본문 정리(공백만이면 빈 문자열)
- 길이 상한
- `반영함` 은 메모 없이는 안 된다

**`lib/emailContent.test.js` (기존)** — `EMAIL_EVENTS` 가 못이라 자동으로 깨진다.
`'의견'` 을 더하는 것은 의도적인 결정이다.

## 범위 밖

**소식 전용 페이지** — `/help#news` 로 충분하다. 페이지를 만들면 라우트와
레이아웃이 하나씩 늘어나는데, 전체 목록을 보러 오는 일은 드물다.

**소식 관리 화면** — 소식은 배포와 함께 나가는 것이라 배포 없이 올릴 일이
없다. 코드에 둔다(`lib/newsItems.js`).

**의견에 답글 주고받기** — 지금은 `반영함` 메모 한 줄이 그 사람에게 가는
것으로 충분하다. 오가는 대화가 필요해지면 그때는 요구사항으로 승격할 일이다.

**점에 숫자 붙이기** — 소식은 "몇 건"이 아니라 "있다/없다"다.
