# 런칭 — 협조 요청

2026-09-09. 목업: `agent/pj/help-request-ideation.html`

---

## 0. 무엇이 문제인가

**막힘을 걸어도 상대가 모른다.** 3단계에서 `@멘션`이 생겼지만 그건 **사람 이름을
알 때** 쓰는 것이다. 실제 상황은 대개 이렇다:

> 물류팀이 정해 줘야 하는데, **물류팀의 누구**인지 모른다.

471건에 담당자는 거의 없고 **역할만** 다 있다. 그 간극이 협조 요청의 자리다.

**재료는 이미 다 있다.**

| | 어디 |
|---|---|
| 역할 (주관·지원·결정권) | `launch_tasks.owner_role` · `support_role` · `decision_org` |
| 역할 → 사람 | `launch_members` (참여자 명단) |
| 항목 링크 | `?task=<코드>` (2단계) |
| 활동 기록 | `launch_task_comments` (3단계) |
| 메일 | `lib/mailer.js` · `sendMailToMany` |

**새로 만드는 것은 컬럼 하나와 라우트 하나다.**

## 1. 자동으로 안 보낸다 — 이 저장소가 이미 판단한 것

`lib/weeklyDigest.js` 맨 위에 이렇게 적혀 있다:

> 방치된 건마다 리마인더를 보내면 지금 당장 25통이 나간다. 그 순간 사람들은
> 규칙을 만들어 걸러 버리고, **그러면 접수 알림까지 같이 죽는다.**
>
> 접수 알림 — 실시간 · "새로 올라왔다"
> 주간 요약 — 주 1회 · "쌓여 있다"
> **이 둘 사이에 개별 리마인더가 낄 자리가 없다.**

막힘으로 바꿀 때 자동 발송하면 **우리가 그 규칙을 깬다.** 막힘 5건이면 5통이고,
내부 사정으로 막은 것까지 나간다.

**협조 요청은 셋째 자리다:**

| | 누가 보내나 | 언제 |
|---|---|---|
| 접수 알림 | 시스템 | 실시간 |
| 주간 요약 | 시스템 | 주 1회 |
| **협조 요청** | **사람** | **보내기로 정했을 때** |

**봇이 아니라 사람이 보낸 것**이라 규칙에 안 걸린다. 그게 이 기능이 사는 이유다.

**반자동(막힘으로 바꾸며 "알릴까요?" 묻기)도 안 한다.** 막힘 = 협조 요청이
아니다. 그 물음이 매번 뜨면 곧 반사적으로 닫게 되고, 그 뒤엔 진짜 물어야 할 때도
안 읽는다.

## 2. 어디서 누르나

| | 무엇 |
|---|---|
| **항목 보기 창** | 한 건을 보다가 그 자리에서 |
| **여러 줄 골라서** | 보드에서 체크해 **한 통에 여러 건**. 지금 「해당없음」 하나뿐인 그 줄의 옆자리 |

**주간 진척은 따로 안 만든다.** 4단계로 거기서도 항목 창이 열리므로 저절로 따라온다.

## 3. 누구에게

**상황에서 미리 고르고, 사람이 바꿀 수 있게 한다.**

| 항목이 | 미리 고르는 역할 |
|---|---|
| 막힘 | `decision_org` (결정권) |
| 선행 대기 | 그 선행의 `owner_role` |
| 그 밖 | `owner_role` (주관) |

막힘의 상대는 거의 늘 결정권이다. 매번 고르게 하면 같은 것을 반복한다.

**역할 → 사람은 `launch_members` 가 안다.** 「물류팀에 요청」이 그 역할로 들어온
참여자들에게 간다. `lib/launchMentionable.js` 의 조회를 역할로 좁히면 된다.

**참여자가 없는 역할은 못 보낸다.** 「재무팀에 참여자가 없습니다 — 명단에 넣으면
보낼 수 있습니다」로 세운다. 짜증나 보이지만 **명단을 채우게 만드는 압력**이고,
지금 참여자가 4명뿐인 것이 그대로 드러난다.

## 4. 안전장치 둘

메일 사용량을 실제로 재 봤다. **협조 요청 자체는 한도 근처에도 안 간다** — 역할당
3~5명이라 회당 3~5통, 하루 다 몰아도 15~50통이고 Gmail 한도(무료 500 · Workspace
2,000 **수신자**/일)의 3~10%다. `sendMailToMany` 가 수신자마다 한 통씩
`Promise.all` 로 쏘지만 transport 를 재사용하고 타임아웃이 짧아(연결 5초 · 소켓
10초) 5명 동시는 문제가 없다.

**그래서 한도 때문이 아니라 사람 때문에 두 가지를 건다.** 한도에 닿기 전에
사람이 먼저 지친다 — §1 의 그 판단이다.

**① 한 번에 20명까지.** 역할을 여럿 골라 30명이 되는 것을 막는다. 넘으면
「너무 많습니다 — 역할을 줄여 주세요」로 세운다. 오발송도 같이 막힌다.
**서버도 같은 상한을 본다** — 화면만 막으면 막은 것이 아니다.

**② 24시간 안에 같은 역할로 또 보내면 알려 준다.** 막지는 않는다. 창이 열릴 때
최근 요청을 한 번 조회해 **보내기 전에** 보여준다:

> 18-22 는 어제 CAIO실에 이미 요청했습니다.

여러 건일 때는 그 항목에 표시를 달아 **체크를 풀 수 있게** 한다. 판단은 사람이
한다 — 정말 다시 보내야 할 때가 있다.

## 5. 데이터 — 새 테이블을 안 만든다

**협조 요청은 댓글이다.** 사람이 쓴 한마디가 본문이고, 그것이 활동에 남아야
다음 사람이 "언제 요청했더라"에 답할 수 있다. 3단계에서 만든 것을 그대로 쓴다.

구별할 수 있어야 하므로(§4②의 24시간 검사, 활동에서 다르게 보이기) 컬럼 하나를
더한다.

```sql
-- 0037: 협조 요청은 댓글이다
--
-- 새 테이블을 안 만든다. 요청의 본체는 사람이 쓴 한마디이고, 그것이 활동에
-- 남아야 "언제 누구에게 요청했더라"에 답이 된다 — 댓글이 이미 그 자리다.
--
-- 이 칸이 비어 있으면 평범한 댓글, 차 있으면 협조 요청이다. 그래서 활동에서
-- 다르게 그릴 수 있고, 24시간 안에 또 보내는 것도 이 칸으로 찾는다.
alter table launch_task_comments
  add column if not exists request_roles text[];

-- 24시간 중복 검사가 (항목, 시각)으로 훑는다. 기존 인덱스가 그 모양이라
-- 새 인덱스는 필요 없다 — idx_launch_task_comments_task (task_id, created_at).
```

**`author` 는 보낸 사람이다.** 시스템이 보낸 것이 아니라 사람이 보낸 것이므로
`null` 로 두지 않는다. 그게 §1 의 요점이다.

## 6. 라우트

```
POST /api/launch/[id]/help-requests
  { taskIds: [uuid], roles: [string], message: string }
GET  /api/launch/[id]/help-requests/recent?taskIds=...
```

**`recent` 는 `roles` 를 안 받는다**(2026-09-09 구현 중 정정). 창이 열릴 때 한 번
부르고, 그때는 사용자가 아직 역할을 안 골랐거나 고르는 중이다. 겹치는 역할을
가리는 일은 화면이 `recentlyAsked(comments, roles)` 로 한다 — 그러면 역할을
바꿀 때마다 서버를 다시 부르지 않아도 경고가 따라 움직인다.

**`recent` 는 404 를 안 낸다.** 항목 하나가 그 사이 지워져도 찾은 것만으로 좁혀
200 으로 답한다. 정보성 호출이라 패널 전체가 「항목을 찾을 수 없습니다」가 되면
안 된다. **보내는 POST 는 다르다** — 거기서는 못 찾으면 404 로 세운다.

둘 다 `requireLaunchAccess(id, 'member')`. `launchRouteGuard.test.js` 가 그 문지기가
있는지는 자동으로 잡는다.

**하지만 `launch_id` 확인은 자동으로 안 잡힌다**(내가 계획에 잘못 적었다).
그 테스트의 부모 범위 검사는 경로에 `[...]` 가 **둘 이상**일 때만 돈다 —
3단계 댓글 라우트는 `[id]/tasks/[taskId]` 라서 걸리지만, 여기는 `[id]` 하나뿐이라
안 걸린다. **`.eq('launch_id', id)` 는 사람이 지켜야 한다.** 두 라우트 모두 걸었다.

**POST 가 하는 일** — 순서가 중요하다:

1. `taskIds` 가 **이 런칭의 것인지** 확인한다(`.eq('launch_id', id)`). 3단계 댓글
   라우트가 같은 것을 하고, 안 하면 주소를 고쳐 남의 런칭에 요청을 넣을 수 있다
2. `roles` 로 `launch_members` 를 좁혀 받는 사람을 **서버가 다시 만든다**.
   화면이 보내온 사람 목록을 믿지 않는다 — `lib/launchMentionable.js` 의 그 규칙이다
3. 받는 사람이 **20명을 넘으면 400**
4. 항목마다 `launch_task_comments` 에 한 줄 (`request_roles` 채움)
5. 인앱 알림 + 메일

**메일은 사람당 한 통이다** — 항목이 여럿이면 그 목록을 본문에 담는다.
항목마다 보내면 3건 × 5명 = 15통이 된다.

**벨도 사람당 하나다.** 링크는 항목이 하나면 `?task=<코드>`, 여럿이면 런칭이다
(여러 코드를 가리키는 필터가 없다). 여럿일 때의 자세한 것은 메일이 담는다.

**알림·메일은 절대 throw 하지 않는다.** `notify.js` 의 규칙 — 메일이 실패했다고
「요청 실패」를 보이면 안 된다. 댓글은 이미 저장됐다.

**제목에 항목 코드를 넣는다.** 메일함에서 무엇에 대한 것인지 알아야 열린다 —

## 8. 앞 단계에서 물린 것 — 이번에 해당하는 것

**① 숫자는 그것이 데려가는 곳과 같아야 한다.** 1단계 두 번, 2단계 한 번.
**이번 위험 지점:** 「5명에게 보내기」라고 적어 놓고 실제로 3명에게만 가는 것.
받는 사람 목록은 **서버가 다시 만들므로**(§6-2) 화면 수와 갈릴 수 있다 —
비활성 팀원이 화면에는 남아 있는 경우가 그렇다. **보낸 뒤 실제 수를 돌려준다.**

**② 조인해서 온 필드는 객체다.** `launch_members` 의 `member` 가 그렇다.
`lib/launchMentionable.js` 의 `mentionableFromMembers` 가 이미 그 처리를 한다 —
다시 쓰지 말고 그것을 역할로 좁혀 쓴다.

**③ 렌더 테스트가 없다.** 브라우저 확인이 검증의 절반이다.

## 9. 안 하는 것

| | 왜 |
|---|---|
| 자동 발송 | §1 |
| 막힘 창에서 함께 묻기 | §1. 막힘 = 협조 요청이 아니다 |
| 주간 진척에 따로 만들기 | 4단계로 거기서도 창이 열린다 |
| 요청 상태 추적 (답변됨/미답변) | 답은 댓글로 온다. 상태를 따로 두면 그 둘이 어긋난다 |
| 재촉(리마인더) | §1 이 막는 바로 그것이다 |
| 참여자 아닌 사람에게 보내기 | 열지도 못하는 사람을 부르면 링크가 403 이다 |

## 10. 테스트

**`lib/helpRequest.js`** (새로) — 순수 부분만.

- `defaultRoles(task)` — 막힘이면 `decision_org`, 아니면 `owner_role`.
  쉼표로 둘 든 값을 나눈다(`splitRoles` 재사용)
- `recipientsForRoles(members, roles)` — 역할로 좁히고 중복 제거.
  한 사람이 두 역할이면 **한 번만**
- `tooMany(count)` — 20 초과 판정
- `recentlyAsked(comments, roles, now)` — 24시간 안에 같은 역할로 나간 것

**`lib/launchRouteGuard.test.js`** — 새 라우트 둘이 자동으로 걸린다.

**브라우저에서 볼 것:**

| | |
|---|---|
| 참여자 없는 역할 | 「명단에 넣으면 보낼 수 있습니다」가 뜨고 못 보낸다 |
| 20명 초과 | 세우고, **서버도 400 을 준다**(주소로 직접 쏴 확인) |
| 24시간 안에 재요청 | 경고가 뜨고, 그래도 보낼 수 있다 |
| 보낸 뒤 | 활동에 한 줄, 벨에 알림, 메일 도착 |
| 여러 건 | **사람당 한 통**에 목록이 담긴다 |
| 실제 발송 수 | 화면이 말한 수와 같다 (§8①) |
