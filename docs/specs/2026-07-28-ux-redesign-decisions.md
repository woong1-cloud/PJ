# UX 개편 결정 기록 (2026-07-28)

로컬 검토 후 나온 결정 사항. 다음 작업의 스펙 작성 출발점이다.

## 배경

전사 멀티브랜드 요구사항 관리 웹앱을 로컬에서 처음 통으로 검토했다. 기능은 다 돌아가지만 완성도가 부족하다는 판단. 지라와 비교했을 때 직관성이 떨어지는 지점을 짚었다.

---

## 1. 상태 체계 재정의 — 확정

### 문제

현재 상태는 7개다: `대기` `요청` `검토` `정책정의` `진행중` `완료` `중복`.

두 가지 결함이 있다.

**`대기`에 행위자가 없다.** 실제로는 "브랜드가 초안을 쓰는 중, 아직 제출 안 함"인데, 이름은 "제출했고 누군가를 기다린다"로 읽힌다. 브랜드와 IT가 정확히 반대로 해석한다.

**`요청`과 `검토`가 서로를 정의한다.** 요청은 "검토를 요청한 것", 검토는 "검토하는 것". 순서를 외우지 않으면 구분이 안 된다.

### 결정

이름을 "누구 차례인지"가 드러나게 바꾸고, `검토`와 `정책정의`를 합쳐 6단계 → 5단계로 줄인다.

| 현재 | 변경 | 누구 차례 |
|---|---|---|
| 대기 | `작성중` | 브랜드 — 아직 제출 전 |
| 요청 | `검토대기` | IT — 아직 안 봄 |
| 검토 + 정책정의 | `검토중` | IT — 보는 중 (두 단계 통합) |
| 진행중 | `개발중` | IT — 만드는 중 |
| 완료 | `완료` | 그대로 |
| 중복 | `중복` | 그대로 (병합 전용) |

`검토대기` / `검토중` 쌍으로 만들면 순서가 이름 안에 들어가 외울 것이 없어진다.

**칸반 컬럼은 6개 → 5개.** 지라 기본이 3개인 것을 감안하면 여전히 많지만, 실무 단계를 반영한 최소 수준이다.

### 색 그룹

상태를 3덩어리로 읽히게 한다.

- `작성중` — 회색 외곽선 (제출 전, 가장 흐리게)
- `검토대기` — 앰버 (IT가 봐야 함, 눈에 띄어야 함)
- `검토중` `개발중` — 파랑 (IT 진행 중)
- `완료` — 초록
- `중복` — 회색 취소선

### 주의

상태값은 텍스트로 저장되어 있어 **기존 행을 전부 갱신하는 마이그레이션이 필요하다.** `검토`와 `정책정의`를 모두 `검토중`으로 합치는 변환도 포함된다. 되돌리기 번거로우니 이름을 확정한 뒤 시작한다.

## 2. 날짜 — 확정

### 배포예상일 (신규)

- **입력 권한은 IT(3차 이상)만.** 브랜드가 희망일을 적으면 의미가 없다.
- 필수값 아님.
- **핵심은 날짜 자체가 아니라 지연 표시다.** 예상일이 지났는데 완료가 아니면 목록에서 빨갛게 띄운다. 이게 없으면 채워넣고 잊는 필드가 된다.

### 완료일 (이미 있음)

`requirements.completed_at`은 `0001_init.sql:53`에 이미 있고, 상태를 완료로 바꿀 때 자동으로 기록된다. **화면에 한 번도 노출되지 않을 뿐이다.** 꺼내 쓰기만 하면 된다.

### 표시 방식

컬럼 하나로 합친다 — 미완료면 예상일, 완료면 완료일. 두 컬럼을 두면 대부분 빈칸이 된다.

---

## 3. 카테고리 · 우선순위 — 확정

계속 쓴다. 다만 **참고용**이므로 사용자가 신경 쓰지 않아도 값이 남아야 한다.

현재 12건 중 9건이 `-`다. 이 상태면 컬럼이 정보가 아니라 노이즈다.

- 우선순위 등록 시 기본값 `중`
- 카테고리 미선택 시 `미분류`

---

## 4. 화면 구조 — 확정

### 브랜드 전환기

`identity.brandId`는 localStorage에 저장되고 `/login`에서만 설정된다. 앱 안에 바꿀 수단이 없어 **로그아웃 → 재로그인이 유일한 경로다.** 현재 어느 브랜드를 보고 있는지 화면에 표시조차 안 된다.

→ 상단에 브랜드 전환기를 상설한다. 전체관리자는 전체 브랜드, 일반 사용자는 배치된 브랜드만.

### 메뉴 3층 분리

현재 6개 링크가 사용자 이름·권한 배지와 한 줄에 평평하게 놓여 있다. 현재 페이지 표시(active)도 없다.

| 층 | 내용 | 위치 |
|---|---|---|
| 컨텍스트 | 브랜드 전환기 | 좌측 상설 |
| 업무 | 요구사항 · 프로젝트 · 대시보드 | 중앙, active 표시 |
| 뷰 | 목록 / 보드 토글 | 페이지 내부 |
| 관리 | 설정 · 브랜드 관리 · 비밀번호 · 로그아웃 | 프로필 드롭다운 |

**`보드` 중복 제거.** 지금 상단 메뉴에도 있고 목록 페이지 우상단 버튼에도 있다. 목록과 보드는 같은 데이터의 두 뷰지 별개 메뉴가 아니다.

## 5. 목록 화면 — 확정

지라 대비 빠진 것들.

- **제목 검색** (현재 없음 — 200건이 되면 못 쓴다)
- **컬럼 정렬** (헤더 클릭)
- **완료·중복 기본 숨김** 토글
- 정보 밀도 개선 (제목 컬럼이 과하게 넓고 여백이 큼)
- 페이지네이션 (현재 전체를 한 번에 그림)

---

## 6. 상태 가이드 — 신규 요청

바뀐 상태 정의를 대시보드에 정리해 노출한다. 각 상태가 무엇이고 누가 다음 행동을 해야 하는지 실무자가 앱 안에서 확인할 수 있어야 한다. 상태 이름을 바꾸는 이유 자체가 "헷갈린다"였으므로, 이름만 바꾸고 설명을 안 두면 절반만 고치는 셈이다.

> 범위 미확정: 대시보드 한 섹션인지, 별도 도움말 페이지인지, 상태 뱃지에 툴팁을 다는 방식인지 정해야 한다.

---

## 7. 사용자 등록 체계 — 검토 결과

**Supabase 대시보드에 수동 등록할 필요는 없다.** `POST /api/admin/create-account`가 `supabase.auth.admin.createUser()`를 호출하고 `team_members.auth_user_id`에 연결한 뒤 `must_change_password`를 켠다. 연결 실패 시 방금 만든 auth 계정을 지우는 롤백까지 있다.

**다만 흐름에 결함이 있다.** 팀원 등록과 계정 생성이 별개 단계라, 현재 팀원 6명 중 4명(이기획·최개발·정뉴발·신입직원테스트)이 계정 없이 남아 있다. 그런데 이기획·최개발은 이미 요구사항의 요청자로 기록되어 있다 — "로그인도 못 하는 사람이 요청자인" 상태가 조용히 만들어졌고 화면에 구분 표시가 없다.

→ 팀원 목록에 `계정 없음` 배지를 달고 그 자리에서 계정을 만들 수 있게 한다.

## 미결정 — 다음 작업 시작 전에 정할 것

1. **상태 가이드의 형태** — 대시보드 섹션 / 별도 페이지 / 툴팁 중 어느 것인가.
2. **사내 배포 환경** — Node 설치된 리눅스인가, Windows인가, Docker인가. ZIP 구성이 여기서 갈린다.
3. **폐쇄망 여부** — 사내 서버가 외부로 못 나가면 Supabase(외부 클라우드)에 접속할 수 없다. 이 경우 현재 아키텍처의 전제가 무너지므로 **가장 먼저 확인해야 한다.**
