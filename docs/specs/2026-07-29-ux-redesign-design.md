어제 확정한 결정(`2026-07-28-ux-redesign-decisions.md`)을 구현 가능한 수준으로 푼 문서다.

**목표:** 기능은 다 되지만 "완성도가 부족하다"는 평가를 받은 화면을, 지라 수준의 직관성으로 끌어올린다.

**전제:** 사내 서버에서 외부 인터넷 접속이 가능함이 확인됐다. Supabase 아키텍처를 그대로 유지한다.

## 1. 상태 체계 재정의

### 1.1 새 상태값

```js
export const REQUIREMENT_STATUSES = ['작성중', '검토대기', '검토중', '개발중', '완료', '중복'];
export const BOARD_STATUSES = ['작성중', '검토대기', '검토중', '개발중', '완료'];
export const MERGED_STATUS = '중복';
export const DONE_STATUS = '완료';
export const INITIAL_STATUS = '작성중';
```

`INITIAL_STATUS`를 새로 내보낸다. 지금은 `POST /api/requirements`가 `status: '대기'`를 하드코딩하고 있어 상수화가 필요하다.

### 1.2 매핑

| 기존 | 신규 | 비고 |
|---|---|---|
| 대기 | 작성중 | 기본값. DB default도 함께 변경 |
| 요청 | 검토대기 | |
| 검토 | 검토중 | 두 값이 하나로 합쳐진다 |
| 정책정의 | 검토중 | |
| 진행중 | 개발중 | |
| 완료 | 완료 | 그대로 |
| 중복 | 중복 | 그대로 |

칸반 컬럼 6개 → 5개.

### 1.3 색 그룹

상태가 3덩어리로 읽히게 한다.

| 상태 | 스타일 | 의도 |
|---|---|---|
| 작성중 | `border border-slate-300 text-slate-500` (배경 없음) | 제출 전 — 가장 흐리게 |
| 검토대기 | `bg-amber-50 text-amber-700` | IT가 봐야 함 — 유일하게 튀는 색 |
| 검토중 | `bg-indigo-50 text-indigo-700` | IT 진행 중 |
| 개발중 | `bg-indigo-50 text-indigo-700` | IT 진행 중 |
| 완료 | `bg-emerald-50 text-emerald-700` | |
| 중복 | `bg-slate-100 text-slate-400` + 취소선 | |

`검토대기`만 앰버인 것이 핵심이다. 목록에서 "지금 내가 손대야 할 것"이 한눈에 보여야 한다.

### 1.4 마이그레이션

```sql
-- 0007_status_rename.sql
alter table requirements drop constraint if exists requirements_status_check;

update requirements set status = '작성중'   where status = '대기';
update requirements set status = '검토대기' where status = '요청';
update requirements set status = '검토중'   where status in ('검토', '정책정의');
update requirements set status = '개발중'   where status = '진행중';

alter table requirements alter column status set default '작성중';

alter table requirements add constraint requirements_status_check
  check (status in ('작성중','검토대기','검토중','개발중','완료','중복'));
```

**순서가 중요하다.** 제약을 먼저 없애야 데이터를 바꿀 수 있고, 데이터를 다 바꾼 뒤에야 새 제약을 걸 수 있다.

#### 함정: `진행중`은 두 테이블에 있다

`project_brands.status`도 `('전개예정','진행중','적용완료')` 제약을 가진다(`0006_projects.sql:23`). 이쪽 `진행중`은 **프로젝트 전개 상태**이며 이름을 바꾸지 않는다.

`UPDATE`의 대상 테이블을 반드시 `requirements`로 한정할 것. 테이블을 잘못 지정하면 프로젝트 전개 현황이 조용히 망가진다.

#### 이 개편은 조용히 실패한다 — 두 지점

**1. 뱃지 스타일 맵은 오류를 내지 않는다.** `RequirementList.jsx:16`이 `STATUS_STYLES[status] ?? DEFAULT_STATUS_STYLE`로 되어 있어, 키를 새 이름으로 못 바꾸면 예외 없이 **모든 뱃지가 회색으로 변한다.** 색 구분이 이번 개편의 핵심인데 리뷰에서 놓치기 쉽다.

**2. 칸반은 모르는 상태의 카드를 버린다.** `KanbanBoard.jsx:68`이 `if (map[r.status])`로 걸러서, 마이그레이션이 안 된 행은 에러 대신 **보드에서 사라진다.** 따라서 DB `UPDATE`와 코드 변경이 같은 배포에 함께 들어가야 한다. 순서가 어긋나면 데이터가 없어진 것처럼 보인다.

두 지점 모두 브라우저 검증 시 명시적으로 확인한다.

#### `change_logs`는 건드리지 않는다

상태 변경 이력이 `change_logs.old_value` / `new_value`에 옛 이름으로 남아 있다. **그대로 둔다.** 실제로 일어나지 않은 일을 기록하도록 이력을 고쳐 쓰는 것이 옛 이름이 보이는 것보다 나쁘다. 이력은 그 시점의 사실이다.

## 2. 날짜

### 2.1 배포예상일 (신규)

```sql
-- 0007에 포함
alter table requirements add column expected_release_date date;
```

- **입력 권한: 3차 이상.** 브랜드 요청자(4차)는 볼 수만 있다. 자기 희망일을 적게 하면 의미가 없어진다.
- 필수값 아님.

전용 엔드포인트를 둔다. 기존 내용수정 라우트에 얹지 않는 이유는 권한 경계가 다르기 때문이다(내용수정은 작성자/브랜드, 날짜는 IT).

```
PATCH /api/requirements/[id]/expected-date
body: { brandId, expectedReleaseDate }   // null이면 해제
requireBrandAccess(brandId, '3차')
```

`change_logs`에 `change_type: '예상일변경'`으로 남긴다. 날짜가 밀리는 것 자체가 추적할 가치가 있는 정보다.

### 2.2 완료일 (이미 있음)

`requirements.completed_at`은 `0001_init.sql:53`에 이미 있고 `PATCH .../status`가 `computeCompletedAt`으로 자동 기록한다. **화면에 노출만 하면 된다. 새로 만들 것이 없다.**

목록 API의 `select`에 `completed_at`과 `expected_release_date`를 추가해야 한다(현재 둘 다 빠져 있다).

### 2.3 지연 판정 — 순수 함수 (TDD)

```js
// lib/overdue.js
export function isOverdue(expectedDate, status, todayIso) { ... }
```

`expectedDate`가 있고, `todayIso`보다 과거이며, 상태가 `완료`/`중복`이 아닐 때만 `true`.

테스트 케이스: 예상일 없음 / 미래 / 오늘(경계 — 오늘은 지연 아님) / 과거+개발중 / 과거+완료 / 과거+중복.

### 2.4 표시 — 컬럼 하나로 합친다

| 조건 | 표시 |
|---|---|
| 상태가 `완료` | `07-25 완료` (회색) |
| 예상일 있고 지연 | `07-25 지연` (빨강 + 경고 아이콘) |
| 예상일 있고 정상 | `08-14 예정` (회색) |
| 그 외 | `—` |

두 컬럼으로 나누면 대부분 빈칸이 된다.

## 3. 화면 구조

### 3.1 브랜드 전환기

**현재 문제:** `identity.brandId`는 `/login`에서만 설정된다. 앱 안에 바꿀 수단이 없어 로그아웃이 유일한 경로이며, 현재 브랜드가 화면에 표시조차 안 된다.

`components/BrandSwitcher.jsx`를 만들어 TopBar 좌측에 상설한다.

- 목록 출처: 전체관리자는 `GET /api/brands`(활성만), 그 외는 `GET /api/my-brands`
- 선택 시 `saveIdentity({ ...identity, brandId, tier })` 후 현재 경로 유지한 채 갱신
- 브랜드가 1개뿐이면 드롭다운 없이 이름만 표시

**주의: tier를 함께 갱신해야 한다.** 등급은 브랜드마다 다르다. 스파오에서 2차인 사람이 미쏘에서는 4차일 수 있다. 브랜드만 바꾸고 tier를 그대로 두면 권한이 잘못 계산된다.

기존 `app/admin/dashboard/page.js:50`의 `goToBrand`가 `tier: '1차'`를 하드코딩하고 있다. 전체관리자 전용 경로라 지금은 우연히 맞지만, 같은 실수를 새 컴포넌트에서 반복하면 안 된다. 대시보드도 새 헬퍼를 쓰도록 바꾼다.

### 3.2 메뉴 재편

| 층 | 내용 | 위치 |
|---|---|---|
| 컨텍스트 | 브랜드 전환기 | 좌측 |
| 업무 | 요구사항 · 프로젝트 · 대시보드 | 중앙, active 밑줄 |
| 액션 | `+ 새 요구사항` | 우측 |
| 관리 | 설정 · 브랜드 관리 · 비밀번호 변경 · 로그아웃 | 프로필 드롭다운 |

- active 판정은 `usePathname()`으로 한다.
- `대시보드`는 전체관리자만(현행 유지).
- **`보드` 링크를 TopBar에서 제거한다.** 목록 페이지 안의 뷰 토글로만 남긴다. 같은 데이터의 두 뷰지 별개 메뉴가 아니다.
- 프로필 드롭다운 안의 항목은 각자의 기존 권한 조건을 그대로 따른다.

## 4. 목록 개편

### 4.1 API 확장 — `GET /api/requirements`

새 쿼리 파라미터.

| 파라미터 | 동작 |
|---|---|
| `q` | 제목 부분일치(`ilike %q%`) |
| `sort` | `request_date`(기본) / `priority` / `status` / `expected_release_date` |
| `dir` | `asc` / `desc`(기본) |
| `includeDone` | `'true'`면 완료·중복 포함. 없으면 **제외** |

`includeDone`의 기본값이 "숨김"인 것이 핵심이다. 지금은 완료된 항목이 목록 상단을 차지한다.

`select`에 `completed_at`, `expected_release_date`를 추가한다.

우선순위 정렬은 `상 > 중 > 하` 순서라 사전순이 맞지 않는다. Postgres 정렬로 풀기 번거로우므로 **정렬은 서버에서 `request_date`만 처리하고 나머지는 클라이언트에서 한다.** 한 브랜드의 요구사항 수는 수백 건 규모이므로 전량을 받아 정렬해도 문제없다.

> 페이지네이션은 이번 범위에서 제외한다. 데이터가 수백 건 규모라 아직 필요 없고, 검색·필터·완료 숨김이 먼저다. 천 건을 넘기면 그때 다룬다.

### 4.2 기본값

- **우선순위:** `POST /api/requirements`에서 미지정 시 `'중'`. 등록 폼의 기본 선택도 `중`.
- **카테고리:** FK라 DB 기본값을 줄 수 없다. 표시 단계에서 `null`이면 `미분류`로 보여준다(현재 `-`).

빈칸이 12건 중 9건인 상태에서는 컬럼이 정보가 아니라 노이즈다.

### 4.3 목록 컬럼

| 컬럼 | 비고 |
|---|---|
| 상태 | 뱃지 |
| 제목 | 비공개·첨부·병합 표시 포함 |
| 카테고리 | `미분류` 폴백 |
| 우선순위 | `상` 빨강 / `중` 앰버 / `하` 회색 |
| 담당자 | **신규** — 지금 없다 |
| 예상·완료일 | **신규** — 2.4의 통합 컬럼 |

`요청일`은 빼고 `담당자`를 넣는다. 요청일은 상세에서 보면 되고, 목록에서는 "누가 들고 있나"가 더 자주 필요하다.

정보 밀도를 높인다 — 행 패딩 `p-2` → `px-3 py-2`, 제목 컬럼에 `max-width` + 말줄임.

### 4.4 검색·정렬 UI

- 필터바 왼쪽에 검색 입력(돋보기 아이콘). 입력은 **300ms 디바운스** 후 조회한다.
- 컬럼 헤더 클릭 시 정렬 토글(asc ↔ desc), 현재 정렬 컬럼에 방향 화살표 표시.
- 필터바 우측에 `완료 숨김` 토글(기본 켜짐).

## 5. 상태 가이드 (대시보드 섹션)

`/admin/dashboard` 하단에 정적 섹션을 추가한다. API 호출 없음.

내용:
1. 5단계 흐름을 가로로 — `작성중 → 검토대기 → 검토중 → 개발중 → 완료`
2. 각 상태별 표: **상태 / 무슨 뜻인가 / 다음 행동은 누가**

| 상태 | 뜻 | 다음 행동 |
|---|---|---|
| 작성중 | 브랜드가 초안을 쓰는 중, 아직 제출 안 함 | 브랜드 — 제출 |
| 검토대기 | 제출 완료, IT가 아직 보지 않음 | IT — 검토 시작 |
| 검토중 | IT가 검토·정책 정의 중 | IT — 개발 착수 |
| 개발중 | 개발 진행 중 | IT — 완료 처리 |
| 완료 | 배포 완료 | — |
| 중복 | 다른 요구사항에 병합됨 | — |

3. `중복`은 직접 지정할 수 없고 중복처리로만 만들어진다는 안내 한 줄.

상태 이름을 바꾸는 이유가 "헷갈린다"였으므로, 이름만 바꾸고 설명을 두지 않으면 절반만 고치는 셈이다.

## 6. 팀원 계정 상태 노출

**현재 문제:** 팀원 등록과 계정 생성이 별개 단계라, 팀원 6명 중 4명이 로그인 계정 없이 남아 있다. 그런데 그중 2명은 이미 요구사항의 요청자로 기록되어 있다. 화면에 이 구분이 없다.

- `/admin/brands`의 팀원 목록에 `계정 없음` 뱃지를 단다.
- 뱃지 옆에 `계정 만들기` 버튼을 두어 기존 `AccountCredentialDialog`를 그 자리에서 연다.
- `GET /api/team-members`가 `hasAccount: boolean`을 내려준다. **`auth_user_id` 값 자체를 내려보내지 않는다** — 화면에 필요한 것은 유무뿐이고, 내부 식별자를 노출할 이유가 없다.

## 9. 작업 순서

의존 관계상 이 순서를 지킨다.

1. **A. 상태 체계** — 마이그레이션 + 상수 + 하드코딩 제거. 다른 모든 작업이 새 상태값 위에서 돌아간다.
2. **B. 날짜** — 컬럼 + API + 순수 함수.
